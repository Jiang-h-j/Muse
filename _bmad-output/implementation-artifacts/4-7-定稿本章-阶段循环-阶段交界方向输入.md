# Story 4.7: 定稿本章 + 阶段循环 + 阶段交界方向输入

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 对某章满意的用户，
I want 定稿本章、无感进入下一章，并在阶段交界处轻量表达走向，
so that 我能持续写下去，并在关键处对故事收尾有唯一的主动控制点。

## 本 story 是 Epic 4 核心创作闭环的收尾（定稿 → 阶段循环 → 交界方向）

4.4 接入首次真实生成、4.5 做实批注/点评/`canImprove`、4.6 接入改进/重生真实链路——正文已能生成、打磨。本 story 补齐**闭环最后一环**：
1. **定稿本章（FR21）**：新增 `POST .../finalize` 端点，`chapter.status="draft" → "finalized"`（列 4.4 已预留、注释明写「4.7 复用」，chapter.py:71-73，**无迁移**）。前端定稿处理器（app.js:3671-3680）从「仅本地置位 + 跳归档」换成真实 POST。
2. **写前上下文改注只读 finalized（FR21 兑现，Jianghj 裁决②）**：`list_recent_chapters` 加 `status='finalized'` 过滤——**定稿后的章节才成为后续创作正式上下文**，未定稿 draft 不注入。这直接兑现 FR21「当前版本成为后续章节创作的正式上下文」的字面语义，并**推翻 4.4 时期的临时做法**（chapter_repo.py:89-113 注释「4.7 定稿未实现前注入 draft 是唯一做法」——本 story 到期，改为按 status 过滤）。
3. **阶段循环 + 阶段交界方向输入（FR22，原型完全缺失/mock，Jianghj 裁决③⑤）**：定稿当前阶段**最后一章**后进入阶段交界方向输入页（原型 `renderStageDirection` app.js:4548 已有 UI 但全是 mock 跳转），用户填方向/直接继续/我想收尾 → **真实触发幕后生成下一阶段规划**（stage_number+1，复用 4.3 `stage_planner` + ARQ/SSE）→ 进下一阶段第一章。阶段内（非末章）定稿则走原型既有「跳归档页 → 下一章卡 → 回 chapters/N」流。

## Acceptance Criteria

1. **定稿本章端点（FR21，epics.md:1029-1031，原型 `data-finalize-chapter` app.js:3671）**：新增 `POST /api/projects/{project_id}/chapters/{chapter_number}/finalize`（同步 REST，**非异步**——定稿不调 LLM，只改 status，无需 SSE）。service `finalize_chapter`：租户守卫 404 → confirmed 前置 400（复用 `_bible_not_confirmed`）→ 章号范围校验 → **本章须已有正文**（`get_chapter` None → 400 `chapter_not_generated`，复用 4.6 错误工厂）→ `upsert_chapter(status="finalized")`（保留现有 `text`/`revision`，只改 status；`upsert_chapter` 已支持传 status，chapter_repo.py:43-86）。返回 `ChapterTextResponse`（含 `status="finalized"`、`revision`、`chapterText`）。**幂等**：已 finalized 再调不报错（重复定稿返回同状态，前端按钮定稿后已隐藏，此为防御）。

2. **定稿后不可再批注/改进（epics.md:1031，UX-DR7）**：定稿后 `chapter.status="finalized"`，前端 reading 态侧栏隐藏反馈表单 + 修订按钮 + 段落 `＋` 触发器——**均已实现**（app.js:3289 `chapterFinalized` 驱动侧栏、:3372 定稿隐藏 `＋`、:1015/2018/2048 GET 恢复读 `status==="finalized"` 置 `chapterFinalized`）。本 story **保留不改**，只需前端定稿成功后置 `chapterFinalized=true` 并重渲染。

3. **写前上下文只读 finalized 章节（FR21 兑现，决策 2）**：`list_recent_chapters`（chapter_repo.py:89）加 `Chapter.status == "finalized"` 过滤——**只把已定稿章节注入下一章写前上下文**，未定稿 draft 不注入。删除/更新该函数注释里「4.7 前注入 draft 是唯一做法」的临时说明，改述为「4.7 起只注入 finalized（FR21 正式上下文）」。`run_context_agent`（steps.py:194 起）调用点不变（仍取最近 N 章，只是 repo 层过滤条件变严）。**边界**：第一章无前序、或前序均未定稿时返空列表（context-agent 仅用全量设定，行为不崩）。

4. **阶段交界方向输入页真实接线（FR22，原型 mock，决策 3/5）**：原型 `renderStageDirection`（app.js:4548）+ `bindStageDirectionInteractions`（app.js:4569）当前三个按钮全是 `goNext()` 跳 `#/projects/demo/chapters/1` mock。本 story 换成真实：① 路由 `#/projects/{id}/stage-direction` 用真实 projectId（当前硬编码 `demo`，app.js:4551/4575/5036）；② 「带着这个方向写下去」提交 `stageDirectionText`、「直接继续」提交空方向、「我想开始收尾了」提交收尾声明——三者都调**下一阶段规划触发**（AC5）；③ 提交后进忙碌/加载态（幕后规划异步，仿 4.3 stage-plan SSE 消费），就绪后进下一阶段第一章输入态。

5. **下一阶段幕后规划真实生成（FR22，决策 5）**：新增 `POST .../chapters/plan-next-stage` 端点（body `{direction?: string}`）→ service `trigger_next_stage_planning`（仿 `trigger_stage_planning` chapter_service.py:101）→ ARQ `plan_next_stage` worker 任务（仿 `plan_first_stage` worker.py:364）→ `stage_planner.plan_next_stage`（仿 `plan_first_stage` stage_planner.py:188，扩展：读上一阶段 `stage_plan`（当前最大 stage_number）+ confirmed 设定 → LLM 出**下一阶段**目标+章骨架，把 `direction` 方向文本作为「读者对下一阶段的走向意愿」注入 prompt）→ upsert `stage_plan`（stage_number = 上一阶段 + 1，复合唯一键天然支持多行）。SSE result 带 `stagePlan`（含新 `stageNumber`）。**「我想开始收尾了」** = direction 传收尾声明文本（如「读者已声明进入收尾阶段，请规划一个能收束主线、走向结局的阶段」），LLM 据此规划收尾阶段。

6. **阶段交界触发条件（决策 3）**：定稿成功后，前端判断「定稿章号 == 当前阶段 `stage_plan.chapters` 长度」（本阶段最后一章）→ 跳阶段交界方向输入页；否则（阶段内非末章）走既有「跳归档页 → 下一章卡回 chapters/N」流（决策 4，app.js:3679 定稿跳 archive + :3944 下一章卡）。**前端须知当前阶段章数**：`chapterStagePlan()`（app.js:3398 已读 stage_plan）提供 `chapters.length`；定稿时比对 `chapterCreationIndex + 1`（当前章号，1-based）与阶段章数。

7. **阶段循环幕后推进对用户无感（FR22，epics.md:1037-1039）**：阶段推进无独立阶段规划页 / 确认弹窗——阶段内下一章定稿即续写下一章（回输入态），阶段末章定稿才出现极轻的方向输入页（唯一控制点、不可省略，FR22）。下一阶段规划在幕后异步生成（用户体感是「填完方向 → 稍候 → 进下一章」），不暴露 stage_number/规划内部。**「直接继续」= 幕后按既有阶段计划推进**（epics.md:1047）——即空 direction 触发下一阶段规划（LLM 按设定+前文自然规划，不受特定方向约束）。

8. **长程一致性不设人为章数上限（NFR4，epics.md:1049-1051）**：多阶段规划不设阶段数/章数上限（`stage_plan` 复合唯一键 `(user_id, project_id, stage_number)` 支持无限阶段，model 已就绪 stage_plan.py:41-48）；`stage_planner` prompt 沿用 4.3「章数由剧情需要决定、不凑数不硬砍」（stage_planner.py:118）。**状态/人物/世界规则/时间线/伏笔的投影防穿帮由 Epic 5 兑现**（本 story 不做投影，见决策 1）——4.7 只保证「定稿章节成正式上下文 + 阶段可无限循环」的结构前提。

9. **定稿态守卫与错误处理**：① 定稿走同步 REST，成功后前端置 `chapterFinalized=true`；失败（4xx/5xx/网络）显示可读错误（复用 `storyErrorText`）、保留 reading 态可重试；② 下一阶段规划走异步 SSE，失败退回阶段交界页（保留方向文本可重试）+ 可读错误；③ 定稿幂等（AC1）——重复调 finalize 不报错。前端定稿按钮点击后即时置忙碌防重复提交。

### 边界与陷阱（防回归）

1. **定稿是同步 REST、非异步**：finalize 不调 LLM（只改 status），走同步 `POST → 返回资源体`，**不入 ARQ、不连 SSE**。区别于 generate/revise/plan-stage（异步 taskId + SSE）。前端 `await finalizeChapter` 直接拿结果，不走 consume 流。
2. **写后投影/章节卡片不在本 story**（决策 1）：finalize **只改 status**，不建 chapter_card/story_state/story_thread 表、不写 data-agent、不做 chapter-commit 投影——全部归 Epic 5 Story 5.2（其 AC 已明写「接 4.7」）。dev 勿在本 story 引入任何投影/归档表逻辑（超范围）。
3. **`list_recent_chapters` 改过滤会影响既有测试**（Task 11 回归项）：改为只读 finalized 后，context-agent 相关测试若造的前序章节是 draft 将召回空——须把测试夹具前序章节改 finalized。这是本 story 唯一「可能打破既有绿灯」的点，务必核对。
4. **多阶段前端映射是最易失控点**（Task 10）：`chapterStagePlan()` + GET stage-plan 当前只取首阶段。多阶段后需取「当前所处阶段」——**V1 建议改 GET 取最新阶段 + 前端 chapterCreationIndex 全局递增**，勿过度设计（单用户内测先跑通首阶段末章→第二阶段最小链路）。**dev 先与 Jianghj 对齐 Task 10 方案再动手**。
5. **阶段交界触发判据**（决策 3，AC6）：定稿章号 == 当前阶段 chapters 长度才进交界页；非末章走归档流。别把「每次定稿都进交界页」——那违反 FR22「阶段内幕后无感」。
6. **「直接继续」= 空方向触发下一阶段规划**（AC7），不是「什么都不做」——空 direction 让 LLM 按设定+前文自然规划下一阶段。三按钮都触发 plan-next-stage，区别只在 direction 文本。
7. **章号范围校验跨阶段放宽**（Task 2）：finalize 不做 stage_plan 长度上界校验（跨阶段章号会超首阶段长度），只校验 `get_chapter` 存在 + `chapter_number >= 1`。
8. **stage_number 不写死**：`plan_next_stage` 的 upsert stage_number = `get_latest_stage().stage_number + 1`，勿复用 `_FIRST_STAGE=1`（那是首阶段专用）。
9. **触发端点并发去重沿用 defer**：plan-next-stage 与 generate/revise/plan-stage 同款「零幂等 + _job_id 不去重」缺口（deferred-work.md:391 族），本 story 沿用 defer，只前端按钮点击即时忙碌防单页双击，后端并发锁归开放注册前加固批次。
