# Story 5.4: 归档页——首屏收起/展开交互 + 章节归档详情

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 浏览归档的用户，
I want 首屏清爽、按需展开我关心的部分、点开单章看详情，
So that 我能自由控制信息密度、不被一屏塞满。

## Acceptance Criteria

**AC1（归档页首屏默认收起，FR25，UX-DR8）**
**Given** 归档页首屏（`#/projects/:id/archive`）
**When** 页面加载
**Then** 首屏为清爽概览——设定圣经区与各阶段章节归档区**默认全部收起**（原型 `archiveProfileCollapsed=true` 预置 + 各阶段在 `renderChapterArchive` 首次渲染时全部 `archiveCollapsedStages.add(index)`，app.js:334-335,3900-3903）。

**AC2（点行标题展开/收起 + 高度动画 + aria + 箭头，FR25，UX-DR8）**
**Given** 我点某行标题（设定圣经区 `data-toggle-archive-profile` / 阶段行 `data-toggle-archive-stage`）
**When** 点击
**Then** 该区展开/收起并带高度动画（`.archive-stage-collapse` 的 `grid-template-rows: 1fr↔0fr` + opacity 过渡，styles.css:3141-3158），`aria-expanded` 与展开态同步、箭头在 ↓（收起）/↑（展开）间切换（app.js:3817-3819,3847-3849）。

**AC3（各可折叠区状态互相独立，FR25）**
**Given** 多个可折叠区（设定圣经 + 各阶段）
**When** 我展开/收起其中一个
**Then** 只影响该区、其余区状态不变——设定圣经由独立布尔 `archiveProfileCollapsed` 控制、各阶段由 `archiveCollapsedStages`（阶段 index 集合）分别控制，互不联动。

**AC4（点章卡片弹章节归档详情弹窗，展示五要素）**
**Given** 我点某章卡片（`data-open-archive-chapter` + `data-open-archive-stage`）
**When** 点击
**Then** 弹出该章归档详情弹窗（`.archive-dialog`，`role="dialog"` `aria-modal="true"`），依次展示真实五要素——本章发生了什么 / 人物变化 / 新增事实与线索 / 尚未解决的悬念 / 章末状态（来自后端 `ChapterCardSummary`），页脚固定文案「这份归档将作为后续章节创作的长期上下文。」（app.js:3775-3796）。关闭弹窗（× / 页脚返回按钮 / 点背板）恢复列表态。

**AC5（点「续写下一章」卡片进入下一章创作输入态，衔接 Epic 4 章节循环）**
**Given** 某阶段仍有未写的章（后端 `stage.missing > 0`）
**When** 我点该阶段的「续写下一章」卡片
**Then** 进入下一章创作输入态——路由到 `#/projects/{projectId}/chapters/{下一章全局章号}`（衔接 Epic 4 章节创作页的输入态渲染），下一章全局章号 = 当前作品已归档章数 + 1（真实数据推导，替代原型 mock 时代的 `chapterCreationIndex + 1` 内存推导）。

**AC6（真实数据驱动，无 mock 残留 / 无渲染崩溃）**
**Given** 归档页消费 Story 5.3 的 `GET /api/projects/{project_id}/archive` 真实聚合数据
**When** 任一阶段含真实章节卡片
**Then** 章节卡片正常渲染、点开详情正常——不因前端字段名与后端契约不一致（后端出参 `chapterCards`，见受控决策 1）导致 `renderChapterArchive` 抛错白屏；空态（无阶段 / 阶段无卡片 / 未确认设定）与加载/错误态（loading spinner / 错误 + 重试）保持 Story 5.3 已建行为不回归。

## Dev Notes

### 本 story 的性质——纯前端交互 story，后端零改动

Story 5.4 是 Epic 5 归档链（5.1 建表 → 5.2 写后投影 → 5.3 归档页聚合读 API → **5.4 归档页交互兑现**）的**纯前端**收尾切片。后端 `GET /api/projects/{project_id}/archive` 聚合端点已由 Story 5.3 做实做透（`routers/archive.py` + `services/archive_service.py` + `schemas/archive.py`），返回 `{profileConfirmed, profileFields, stages:[{stageNumber, title, completedCount, chapterCards:[五要素], missing}]}`。**本 story 不新增/不改动任何后端路由、service、schema、model、migration**——只在 `prototype/app/app.js`（必要时 `styles.css`）上把归档页交互接对、修好、验证。

### 现状代码事实（Story 5.3 review patch 已落但未浏览器验证——本 story 的真实起点）

Story 5.3 的 review patch（当前工作树未提交，见 `git status`）已把归档页前端从 mock（`archiveStoryProfileFallback` 硬编码 12 字段 + `archiveStagesForPreview` 硬编码 4 章 preview）**改成消费真实 `archiveApi.get(projectId)`**，并保留了原型的折叠/展开/详情弹窗 HTML/CSS/交互。**但 Story 5.3 Completion Notes 明确记载「Chrome headless 网络服务在本机崩溃，因此不把浏览器 UI 自动验证记为通过」**——即这段前端接线**从未在浏览器里真正跑过**。因此遗留两个 5.4 必须兑现的缺口：

### AC5「续写下一章」的真实路由推导（本 story 最需要动脑的点）

原型/HEAD 的 `[data-start-next-chapter]` handler（app.js:3974-3997）路由到 `#/projects/${nextProjectId}/chapters/${chapterCreationIndex + 1}`，用的是**内存态变量** `chapterCreationIndex`（章节创作页维护的全局 0-based 章序）和 `chapterProjectId || explorationProjectId || "demo"` 兜底链。但**归档页是从真实 API 直接加载的独立入口**（用户可直达 `#/projects/:id/archive`，不经过章节创作页），此时：
- `chapterCreationIndex` 是上一次创作页的残留值（可能是 0 或任意旧值），**不可信**；
- `chapterProjectId`/`explorationProjectId` 可能为空 → 落到 `"demo"` 占位路由（错误）。

**正解**：路由 projectId 用 `archiveProjectId`（app.js:3862 加载时已存真实作品 id）；下一章全局章号用真实归档数据推导——已归档总章数 + 1。`renderChapterArchive` 已算出 `completedCount = stages.reduce((t,s)=>t+s.completedCount,0)`（app.js:3904-3907），下一章号即 `completedCount + 1`（也可用全部 `chapterCards.chapterNumber` 最大值 + 1，两者在顺序创作下等价）。这样归档页直达也能正确进「下一待写章」的创作输入态。章内态复位块可沿用 handler 现有代码。

### ⚠️ 已知依赖 / 范围边界：跨阶段真实归档被后端 deferred blocker 阻断

`deferred-work.md:5`（Story 5.3 review 的 defer）登记：后端 `trigger_chapter_generation` / `trigger_chapter_revision` 恒按**第一阶段**计划校验章号（`chapter_service.py:242-247,315-320`），进入第二阶段生成全局第 3 章时会被 `chapter_out_of_range` 拒绝，导致**无法正常产生跨阶段的真实 `chapter_card`**。该修复属独立的「归章节阶段定位修复切片」，**不在本 story（5.4）范围**。

对本 story 的影响：真实环境里目前多半只能产出**第一阶段**的章节卡片。因此：
- Task 4 浏览器验证的多阶段展开/收起路径，现实数据可能只有 1 个阶段可测；可用「造数据」（直接在库里插多阶段 `chapter_card` + 对应 `stage_plan`，或 mock API 响应）验证多阶段折叠独立性（AC3）与 Task 1 修复的健壮性。
- 本 story **不因该 blocker 扩范围去修后端阶段定位**；只在 Dev Agent Record 如实记录「多阶段真实数据受 deferred blocker 限制、以造数据验证」即可，不谎报。

### 受控决策（本 story 定档，沿用先例）

1. **字段错配修法 = 前端改读 `stage.chapterCards`，不加转换层**：对齐 `api.js:11-14` 既定约定「不写 snake↔camel 转换器、直接用后端 camelCase 字段」。后端 `chapter_cards`（schema 内部 snake）→ 出参 `chapterCards`（CamelModel）是正确契约，前端应对齐契约名，而非在前端造 `chapters` 别名或加 map 转换。
2. **不恢复 `data-preview-next-stage` mock 预览钩子**：该钩子是 HEAD mock 时代「多阶段排版预览」的演示态（handler 仅改 DOM 文案、无真实语义，app.js:3998-4003）。真实数据下阶段由后端 `stages` 驱动、无「预览阶段」概念，故不恢复，其悬空 handler 可清理。真实「规划下一阶段」交界流程是 Epic 4 Story 4.7 的 stage-direction 页职责（`renderStageDirection`，app.js:4592+），不在归档页重造。
3. **纯前端 story、后端零改动**：延续 Epic 5「5.3 后端聚合 API + 5.4 前端交互」的读路径拆分（epics.md:1057 依赖链 5.3→5.4）。
