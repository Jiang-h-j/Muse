# Story 4.2: 五段流水线编排底座（V1 四段 + 去 AI 味词表）

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Muse 后端开发者，
I want 一条自建的、可断点续跑的章节生成流水线与正式去 AI 味词表，
so that 章节正文能在可控、可重入、成本可计的运行时上真实生成并自查文风。

## Acceptance Criteria

> 来源：epics.md:889-915（Story 4.2）+ AR11 编排运行时（epics.md:122、architecture.md:189-193）+ AR15 文风锚定（epics.md:129、architecture.md:203-217）+ NFR1/NFR2/NFR5/NFR7b + Epic 4 关键边界①②③（epics.md:859）。

**AC1 · 自建轻量流水线 V1 四段（AR11）**
Given 盲测已通过（4.1 门禁放行——GATE=PASS，创始人 2026-08-04 已正式确认，见 `4-1-*.md` Completion Notes:193-194）
When 搭建编排运行时（AR11，非 LangGraph）
Then 实现自建轻量流水线 V1 **四段**：`context-agent（组装写作任务书）→ drafter（起草正文）→ reviewer（审查）→ polisher（去 AI 味自查自改）`；**data-agent 写后投影不在本 story**（归 Epic 5 Story 5.2）。四段落进 `backend/src/muse/orchestration/`（当前空目录，本 story 首次落地）。

**AC2 · 每段幂等可重入、状态落 PG、断点续跑（AR11 + NFR5）**
Given AR11 要求「每 step 幂等可重入、状态落 PG（天然断点续跑）」
When 流水线执行中某 step 失败、被 ARQ 重试
Then 编排运行状态（run 级 + 各 step 状态 + 各段中间产物）**落 PG**；重跑时**已完成的 step 直接复用其落库产物、只从失败 step 续跑**（不从头重跑四段），成本按 step 累计（NFR5）。这需要一张**最小编排运行状态表**（见 Dev Notes「断点续跑落地方案」——基础设施表，不属 Epic 4「按需建表：无」约束的业务表范畴）。

**AC3 · 正式去 AI 味词表落地进 src（NFR7b clean-room）**
Given 正式去 AI 味词表随本 story 落地（复用自 webnovel-writer polish-guide 的**规则思路**）
When 实现 polisher step
Then 正式词表进 `backend/src/muse/`（供业务链路 polisher 调用），加载**200+ 词黑名单 + 7 层句式规则**（在 4.1 临时子集基础上扩充到该规模），由 polisher 自查自改；**clean-room 重实现——借规则思路、不复制 GPL 源码**（词条与正则本项目独立编写，NFR7b，architecture.md:250-252）。**保持 4.1 装置消费的接口兼容**（`analyze_axis_b` / `LEXICON_VERSION` / `BLACKLIST_WORDS` / `PATTERN_RULES`），使盲测脚本与其单测零回归（见 Dev Notes「词表升级迁移策略」）。

**AC4 · style_profile 作风格锚点注入 drafter + polisher 叠加自查（AR15，兑现 NFR1）**
Given style_profile 是每章生成的风格锚点（AR15，Story 3.2 已抽取、落 story_bible.style_profile）
When drafter 生成正文
Then style_profile 作为**风格锚点段**注入 drafter 的写作任务书；与去 AI 味词表叠加、由 polisher step 自查自改，**共同兑现 NFR1 文字质量红线**。drafter 写前上下文读 `status='confirmed'` 的 story_bible 行（12 字段全文 + style_profile）；**V1 写前上下文用「全量设定 + 最近定稿章节」直接注入，不接 RAG**（RAG 三级召回归 Epic 5 回头增强，epics.md:859③）——本 story 尚无定稿章节表，故 V1 写前上下文 = 全量设定（confirmed 12 字段 + style_profile），最近定稿章节注入点预留、由 4.4/Epic5 接入。

**AC5 · 异步任务模型（POST→taskId→GET events SSE，NFR2）**
Given 章节生成是多次 LLM 调用叠加（5–10 次/章，NFR2）
When 流水线运行
Then 走异步任务模型：新增 ARQ 任务 `generate_chapter`（承 `demo_generate` / `settle_exploration` 范式，worker.py），**每段作为一个 step 推 progress 事件**，末段推 result（章节正文），异常推 error（复用错误 envelope）；**不同步阻塞、不前端轮询**。任务函数注册进 `WorkerSettings.functions`（worker.py:214）。

**AC6 · 范围克制——纯后端底座 + 装置验证，不接用户可见入口（受控决策，创始人 2026-08-04 授权自主定夺）**
Given epics 里线性依赖 4.2→4.4；4.4 才做「真实生成章节正文、替换前端 mock、本章想法输入、前端接线」
When 界定本 story「底座」范围
Then 本 story **只交付**：四段 service + 编排器 + 正式词表(进 src) + 编排运行状态表(迁移) + ARQ `generate_chapter` 任务 + 离线单测/脚本装置跑通产样。**不交付**：用户可见 POST 生成端点（`POST /api/projects/{id}/chapters/{n}/generate`）、本章想法输入、前端接线、章节正文正式落业务表——**全留 Story 4.4**。本 story 用**开发脚本 / 单测**驱动流水线跑通并产样验证（仿 4.1 装置精神），验证「四段串起来能出一章符合红线的正文」即达标。

**AC7 · 记账正确性（每段走 MeteredProvider，NFR5 + AR14）**
Given 每段各调一次 LLM、成本须按 step 累计（NFR5）、记账埋点在 Provider 层（AR14）
When 各段拿 provider
Then **每段一律走 `get_provider_for_user(session, user_id, project_id=project_id)`** 拿被 `MeteredProvider` 包裹的 provider，绝不自行 `new DeepSeekProvider`（否则漏记账）；每段 `.chat()` 自动 `record_usage` 一笔，天然累加到 `usage_ledger`（按 project_id 可汇总单章成本，供回填免费额度阈值，settings.py:69）。护栏 `check_quota` 在**每段 provider 调用之前**（托管触顶抛 429 → 转 error 事件）。

## Dev Notes

### 本 story 的性质：纯后端编排底座，不接用户可见入口（AC6 范围边界）

这是 Epic 4 的**运行时地基**——把 4.1 盲测验证过的「单段 drafter 产样」升级为**可断点续跑、成本可计、带正式词表自查的四段流水线**，但**不接用户入口**。用户可见的 POST 生成端点、本章想法输入、前端接线、章节正文正式落业务表**全归 4.4**（epics.md 线性依赖 4.2→4.4）。本 story 用脚本/单测驱动跑通产样即达标。**严守边界**：不做前端、不做 POST 端点、不做 data-agent 第五段（Epic 5）、不接 RAG（Epic 5）。

### 断点续跑落地方案（AC2——解「AR11 要落 PG」vs「Epic 4 按需建表：无」的张力）

**决策（创始人 2026-08-04 授权自主定夺，依据 [[feedback_design_decision_delegation]]）**：新建一张**最小编排运行状态表** `chapter_generation_run`（Task 2）。理由：
- AR11 明确要求「每 step 幂等可重入、状态落 PG（天然断点续跑）」（epics.md:122、architecture.md:189-193）——这是**基础设施**需求，不落库就没有断点续跑。
- Epic 4「按需建表：无」（epics.md:858）指的是**业务表**（章节正文 / chapter_cards——那些归 4.4 / Epic 5）；**编排运行时状态表是基础设施表**，两者边界不冲突。architecture.md:192「step 间状态落 PG（天然实现断点续跑）」是本表的架构依据。
- 表设计求最小：run 级状态 + 各段状态/产物（JSONB）+ 幂等键 `(user_id, project_id, chapter_number)`。够「失败只续跑失败段」即可，不过度设计。
- **替代方案（不选）**：四段在单 ARQ 任务里顺序跑、失败整任务重试（从头跑四段）——最轻、最贴「按需建表：无」，但 AR11「段级断点续跑」卖点没兑现，且四段每段都要钱（NFR5 成本累计），从头重跑=重复付费。故选建表方案，真正兑现 AR11。
