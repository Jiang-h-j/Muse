# Story 2.8: 自由探索——设定导航、按需回答思路与 7 项完成度门禁

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 自由探索中的用户，
I want 系统主动判断故事设定还缺什么、每轮只问一个具体问题，并在我卡住时给出可选思路、允许我跳过，
so that 我不会被同一个话题无限追问，也不会在设定还没聊清楚前就被允许草草整理。

> **2026-07-31 Correct Course 新增**（`_bmad-output/planning-artifacts/sprint-change-proposal-2026-07-31.md`）：把 EXP-P02「以设定结果覆盖度决定探索是否完成」的最小能力从 V2 提前到 V1，替换 2.7 的「≥1 条用户消息」近似门禁。**不回滚** 2.6/2.7 已交付的真实聊天/线索/初版门禁——本 story 在其基础上新增导航能力；`free/settle` 端点的路径与返回契约不变，只是门禁判据从「≥1 条消息」升级为「7 项主干全 filled/skipped」。

## Acceptance Criteria

> 源自 `epics.md#Story 2.8`（L655-707）与 Sprint Change Proposal §5.4/§5.6。本 story **纯后端**（受控决策 A 延续 1.7→2.7 既定方法论）：`prototype/app/app.js` 零改动，消费本 story 后端能力的前端接线由 **Story 7.6**（已在 in-progress、暂停等待本 story）承接。

1. **[导航状态持久化]** **Given** 自由探索需要判断「设定整理所需信息是否已经充分形成」（FR10，EXP-P02 V1 最小能力）
   **When** 会话建立（`enter_exploration` 首次创建 free 会话）
   **Then** `exploration_session.guidance_state`（JSONB）持久化一份 7 项通用主干字段（`genre`/`core_appeal`/`protagonist`/`main_conflict`/`world_rules`/`overall_tone`/`opening_hook`——与 `story_bible`/`story_settle_agent._BACKBONE_FIELDS` 同一 key 集合、同一顺序）的完成度状态，每项取值 `missing`/`filled`/`skipped`，初始态全 `missing`；随对话与线索刷新，不依赖前端本地态（sessionStorage）作为真相源。

2. **[单项下一问推进]** **Given** 用户已有对话与线索材料
   **When** 一轮自由对话结束（即 `stream_free_chat` 该轮 `done` 后）
   **Then** 系统按当前材料更新 7 项状态、只选择一个当前最缺的项、生成围绕该项的一句具体问题；已 `filled` 或 `skipped` 的项本轮不重复提问。

3. **[零对话四入口→开场问题]** **Given** 用户尚无任何对话（FR9 起点）
   **When** 用户选择「先说一个故事想法 / 先聊主角 / 先定核心冲突 / 先想世界与氛围」四个入口之一
   **Then** 系统据该入口生成对应维度的第一个具体问题，作为本轮对话的开场；四个入口是固定产品入口，不是 AI 生成的建议（后端只需接收入口标识、生成对应首问，不负责渲染入口本身——那是 7.6 前端职责）。

4. **[按需回答思路]** **Given** 用户面对当前具体问题不知道怎么答
   **When** 用户点击「没想好？看看几个思路」
   **Then** 系统按需调用一次 LLM，生成 2–4 个与当前问题、已有线索和缺失字段相关的回答选项；**不在每轮自动生成**，避免不必要的调用成本。

5. **[选项直接提交]** **Given** 用户点击某个 AI 回答思路
   **When** 该选项被选中
   **Then** 系统把它直接作为本轮用户回答提交（等价于用户自己发送该消息，复用 `stream_free_chat` 同一持久化+刷新链路），立即触发完成度与线索的刷新。

6. **[跳过 + 谨慎归纳写入线索]** **Given** 用户对当前问题选择「先跳过这个问题」
   **When** 跳过被触发
   **Then** 该项标记为 `skipped`；系统据已有材料做一次谨慎归纳写入对应 `story_clue` 槙位（不杜撰；无材料可归纳则该槙位保持「尚未确定」空值，不强行编造），随后不再围绕该项重复追问，直接推进到下一个缺失项或收束。**跳过归纳只写未被用户编辑（`user_edited=false`）的槙位**——已被用户手动编辑的槙位永不被本操作覆盖，与 2.6 `extract_clues`/`refresh_clues` 同一硬约束（AC10）。

7. **[7 项完成→收束开放]** **Given** 7 项主干均已 `filled` 或 `skipped`
   **When** 状态刷新完成
   **Then** `readyToSettle` 置真，Agent 在对话流中给出明确收束提示（如「这本故事的骨架已经够清楚了，现在可以整理成一份设定卡」）；系统不再主动抛出新问题。

8. **[后端硬门禁替换 2.7 近似判据]** **Given** 「整理为故事设定」触发端点（复用 2.7 的 `POST .../free/settle`，路径/返回契约不变）
   **When** 请求到达且 7 项主干尚未全部 `filled`/`skipped`
   **Then** 后端硬校验拒绝（400 `exploration_not_ready`，与既有 2.7 错误族同码复用），不入队、不登记属主、不消耗整理任务；**2.7 的「≥1 条 free user 消息」判据被本 story 完全替换**（不再是「或」的关系，是替换关系——7 项未齐即 400，即便已有远超 1 条的消息）。前端 disabled + 后端硬校验双防线（延续既定方法论）。

9. **[特化字段与文风锚点不阻塞]** **Given** 题材特化字段（力量体系/金手指/感情线/势力格局）与文风锚点
   **When** 判断 7 项主干完成度
   **Then** 特化字段与文风锚点不计入本门禁、不阻塞整理（FR10）。

10. **[租户隔离 + LLMProvider 抽象 + user_edited 保护]** **Given** 探索会话数据（NFR3）与 `story_clue.user_edited` 保护（2.6 既有硬约束）
    **When** 任意读写导航状态、或导航生成的问答更新线索
    **Then** 以 `user_id` + `project_id` 行级隔离，不越权访问他人会话；结构化生成与建议均经 `LLMProvider` 抽象，禁止直接调用 openai SDK（AR12）；已被用户手动编辑（`user_edited=true`）的线索行不被覆盖；导航状态与线索区各自持久化、职责边界不合并——`story_clue` 仍是用户可编辑事实源，`guidance_state` 只服务完成度与下一问的后端事实源。

### 架构与既有模式（务必先读代码再动手，不要凭空实现）

**分层与既有约定（architecture.md）**：`routers`（仅校验+分发）→ `services`（业务）→ `repositories`（数据+租户守卫）。所有业务表带 `user_id`+`project_id`（NFR3）。出入参 camelCase、内部 snake_case，转换点唯一在 `schemas/` 层——**本 story 的 `guidance_state.fields` dict 内部 key 是这条约定的唯一已知例外**（Task 8 已详细论证：dict 的 key 不经 `alias_generator` 转换，若要让前端拿到 camelCase 字段名、落库时就需直接用 camelCase 字符串作 dict key）。这是本 story 需要 dev 在实现时最先拍板的技术决策，影响 Task 2/3/4/6/8 的具体字符串常量选取，**建议在开始编码前先写一个最小 Pydantic 验证脚本确认行为**，而非凭直觉假设。

**guidance_state 持久化载体的定位（architecture.md L237 已定档，不可偏离）**：`exploration_session.guidance_state`（JSONB），**不与 `story_clue` 合并**——`story_clue` 仍是用户可编辑事实展示区，`guidance_state` 只服务完成度与下一问的后端事实源。但 AC6「跳过后谨慎归纳写入线索」意味着 `skip_current_field` 这一个操作**同时触碰两个存储**（`guidance_state.fields[x]=skipped` + 可能的 `story_clue.value` 更新）——这不违反"不合并"原则（两处仍是独立更新语句、独立语义），只是同一次用户操作的两个连带效果，仿 2.2 `enter_exploration` 同一事务内既建会话又播种线索的先例（不同存储各司其职，同一编排流程内先后写）。

**与 2.6/2.7 的关系（净新增而非重造）**：本 story **不改** `stream_free_chat` 的对话流式主链路（消息落库、SSE delta/done/error 编码不变），只在其 `done` 之后**追加一次** `refresh_guidance` 调用（Task 3）。**不改** `free/clues` CRUD 四端点（GET/POST/PATCH/DELETE）——线索仍由用户直接编辑或 `extract_clues`/`refresh_clues`（2.6 既有）自动整理，Task 6 的跳过归纳是**第三条**写入线索的路径（与既有两条并存，同样受 `user_edited` 保护）。**改**的只有：`_PRESET_CLUES`/`PRESET_CLUE_KEYS` 常量扩容（Task 1）、`trigger_free_settle` 门禁判据替换（Task 7）。

**`refresh_guidance` 调用时机的关键设计取舍（Task 3 步骤 8 的护栏降级处理，务必理解）**：`stream_free_chat` 是**用户能直接感知的对话主链路**（SSE delta/done），`refresh_guidance` 是它 `done` 之后的**副作用**（完成度判定+下一问）。若 `refresh_guidance` 内的 `check_quota` 触顶抛 429，若直接让异常冒泡，会导致——对话本身已成功（用户消息+Agent 回复都已落库、SSE 已收到 `done`）——但紧接着的完成度刷新失败、前端可能因未处理这个"done 之后还有一步可能失败"的时序而卡住或误报"消息失败"。**故 Task 3 步骤 8 要求护栏 429 时静默降级**（返回当前已持久化态、不更新 `current_question`），而不是让整轮对话因为"追问逻辑"这个增值功能而报错。这是本 story 相对 2.6/2.7 的一个新交互形态（"主链路成功、副作用降级"），dev 实现时注意不要把 `refresh_guidance` 的异常处理和 `stream_free_chat` 的异常处理混为一谈——两者是不同粒度的失败容忍策略。

**为什么 `refresh_guidance` 不做成前端可直接调用的端点、而是 `stream_free_chat` 内部调用**（回应 Task 8 中 `POST .../guidance/refresh` 端点存在性的疑惑）：AC2 明确「一轮自由对话结束」触发刷新，这是"每轮对话的自然后续"，不是用户主动操作。但 Task 8 仍保留一个 `refresh`端点（或改 `GET .../guidance` 恢复端点，dev 自行决定）作为**前端断线重连/刷新页面时的状态恢复入口**——此时前端不是要"触发新一轮判定"，而是要"读到当前已持久化的状态"。这两个用途（对话副作用触发 vs 页面恢复读取）**语义不同**：前者应该是 `stream_free_chat` 内部直接调用 `guidance_agent.refresh_guidance` 的**函数调用**（不经 HTTP），后者才是暴露给前端的**只读恢复端点**（更接近 `get_pending_card`/`GET .../free/messages` 的既有恢复语义）。dev 实现时如果发现`GET /free/guidance`（纯读取，不重新调 LLM）与本 story Task 8 描述的 `POST .../guidance/refresh`（会重新调 LLM）两个概念被混淆，请以本段落为准分离成两个不同的函数/端点：一个是`refresh_guidance`（有 LLM 调用副作用，被 `stream_free_chat` 内部调用，**不必**独立暴露 HTTP 端点，除非 7.6 前端确实需要一个"强制重新判定一次"的兜底按钮——若无该产品需求，Task 8 的 `refresh` 端点可以整个不做，只留 `GET /free/guidance` 纯读取恢复端点）。**这是本 story 留给 dev 的一个范围裁量点**，需在 Completion Notes 写明最终端点集合与理由。

**skip 与 suggestions 的护栏取舍对比**：`suggest_answers`（Task 5）触顶 429 应直接报错（这是用户主动点击"看看思路"这个增值操作，失败了大不了不看，无副作用可容忍）；`skip_current_field`（Task 6）的取舍更微妙——跳过这个"状态转移"动作本身（`fields[x]=skipped`）不该被额度门禁挡住（用户明确要跳、不该被迫卡住），但"谨慎归纳"这个 LLM 调用可以失败降级（不归纳、槙位留空）。这两者的处理优先级不同：`skip` 优先保证状态转移成功，`suggestions` 优先保证有货才返回。
