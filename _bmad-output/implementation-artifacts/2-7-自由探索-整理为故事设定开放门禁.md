# Story 2.7: 自由探索——「整理为故事设定」开放门禁

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 自由探索中的用户，
I want 只有在真正聊出内容后才能整理成故事设定，
so that 我不会在信息不足时得到一份空洞的设定。

## Acceptance Criteria

> **净新增能力 = AC3 的后端（自由探索「整理为故事设定」触发端点 `POST /{project_id}/explore/free/settle` + 复用 2.5 的 skeleton `settle_guided_exploration` 任务或新建等价 free 任务，走 ARQ 后台异步）+ 后端门禁硬校验（≥1 条 free user 消息才允许触发）。** AC1/AC2（按钮首屏 `disabled`、提示文案随 `canFinish` 切换）是**原型已实现的前端交互契约**（FR10、UX-DR5，页面即契约），事实源是 `prototype/app/app.js:901-919`（`canFinish = freeConversation.some(role==="user")`、`formingHint` 两态文案、`finish-exploration` 按钮 `disabled` 属性），本 story **不改 `app.js`、不回归这些契约**——延续 2.3/2.4/2.5/2.6 受控决策 A（后端优先、前端接线 defer 至同一「探索前端集成切片」）。本 story 只交付后端：① 自由探索整理触发端点（租户守卫 + `_require_project_mode(project, "free")` + **门禁硬校验** + 登记属主 + 入队 ARQ 任务，返 `taskId`）；② 门禁在后端做实（信息不足则 400 拒绝，不止于前端按钮 disabled）。

1. **Given** 我刚进入自由探索、只有开场白（FR10，UX-DR5）
   **When** 页面渲染「整理为故事设定」按钮
   **Then** 按钮首屏不可用（`disabled`），提示「继续和 Agent 讨论，线索足够时就能整理为故事设定。」（原型 `app.js:902-904,918-919`）。**本 story 后端 only，此前端交互契约由原型保持、不回归。**

2. **Given** 我已至少发送一条消息（`canFinish = freeConversation.some(entry => entry.role === "user")`，原型 `app.js:901`）
   **When** 按钮状态刷新
   **Then** 按钮开放可点，提示转「故事线索已经足够，可以整理成一份故事设定。」（原型 `app.js:902-904`）。**本 AC 完全是前端状态与静态文案切换（原型无 fetch）——本 story 不回归此契约。** 后端提供的对应能力见 AC4 的门禁硬校验（前端 disable 与后端 400 是同一门禁的两道防线）。

3. **Given** 我点开放后的「整理为故事设定」
   **When** 触发整理
   **Then** 后端以 ARQ 后台任务启动整理（异步，非交互式流式——异步模型二分 epics.md:457），交接 Epic 3 承接设定候选卡（方案 A 边界）。**本 story 交付**：`POST /{project_id}/explore/free/settle`（提交语义，返 200 + `taskId`，**非** `EventSourceResponse`），前端拿 `taskId` 后连 2.1 已建的 `GET /api/tasks/{taskId}/events` 消费 `progress`/占位 `result`/`error`（复用 2.1 SSE 消费端点，不重建）；任务体真实调用 LLM 把对话/线索凝练成 12 字段设定候选卡的部分归 **Story 3.3**（本 story 任务体是 skeleton 或复用 2.5 skeleton，只推占位 result 证明「触发→ARQ→worker→SSE」全链路跑通，受控决策 B/C）。**前端发起 POST + 连 SSE 消费 defer 至探索前端集成切片**（受控决策 A）。

4. **[后端门禁硬校验] Given** 本 story user story 的 benefit 是「信息不足不产出空洞设定」，且 2.6 已确立「模式独立在数据写入层真正落地，不止于前端不提供入口」的先例
   **When** `POST /{project_id}/explore/free/settle` 被调用
   **Then** 触发端点在租户守卫 + mode 守卫之后，**再校验本会话至少有 1 条 free `role="user"` 消息**（V1 用「≥1 条用户消息」近似门禁，AC5 边界）；不满足则拒绝（`ErrorEnvelope(code="exploration_not_ready", message="继续和 Agent 讨论，线索足够时就能整理为故事设定。", http_status=400)`），**不入队、不登记属主、不返 taskId**。满足则照 AC3 正常触发。**门禁在 API 层真正落地**（不止于前端 disable），与 2.6 mode 守卫「数据写入层真正落地」同源精神。**注意此为本 story 与 2.5 guided settle 的显式差异**：2.5 skeleton「不校验是否有引导答案、空答案也能跑管道」（受控决策 C）；本 story 因门禁是 user story 核心语义（FR10 明写「须补足信息…才开放」），后端做实门禁，非纯前端约束。

5. **Given** 边界说明（V1 门禁近似）
   **When** 界定 V1 开放条件
   **Then** V1 用「≥1 条 free user 消息 + 主动点按钮（前端）/ 后端 400 门禁」近似；真正的覆盖度/置信度门禁属 EXP-P02（V2），不在本 story——不做「凑齐 N 个线索/覆盖度打分才放行」这类重门禁（YAGNI）。

## Dev Notes

### 架构与既有模式（务必先读代码再动手，不要凭空实现）

**分层与既有约定（architecture.md）**：`routers`（仅校验+分发）→ `services`（业务）→ `repositories`（数据+租户守卫）。所有业务表必带 `user_id`+`project_id`（NFR3）。出入参 camelCase、内部 snake_case，转换点唯一在 `schemas/` 层（`TaskSubmitResponse` 的 `task_id → taskId` 即此约定）。本 story **不调 LLM、不建表、不加迁移**——纯新增一个触发端点 + 一条 service + 一个 repo 门禁原语 + 测试。

**异步模型二分（epics.md:457，本 story 只用 ARQ 后台任务这一半）**：
- 交互式对话（自由聊天 2.6、引导自述理解 2.3）→ `LLMProvider.stream` 直连流式 SSE，返 `EventSourceResponse`。
- 「整理为故事设定」凝练（2.5 guided settle、**本 story free settle**）→ **ARQ 后台任务** `POST→taskId→GET /events`，返 `TaskSubmitResponse`（**非** `EventSourceResponse`）。**本 story 属后者**——整理是长时凝练（3.3 接真实 LLM 后更明显），走 ARQ，前端拿 taskId 连 2.1 SSE 消费端点。**切勿误做成流式端点**（那是 free messages 2.6 的模式）。

**`trigger_guided_settle` 是本 story 的直接模板（`services/exploration_service.py:180-221`，逐行照搬）**：租户守卫（`get_owned_project`→404）→ mode 守卫（`_require_project_mode`）→ [本 story 在此**插入门禁校验**] → `uuid.uuid4().hex` 生成 task_id → `create_pool` → **先 `register_task_owner` 再 `enqueue_job`**（陷阱②：顺序错则 worker 可能在属主键写入前发首个事件、SSE 端点鉴权读不到属主而对合法属主误返 404）→ `finally: aclose()`。本 story `trigger_free_settle` 只在模板上改两点：mode 由 `"guided"` → `"free"`；插入 `has_free_user_message` 门禁（2.5 无此步）。

**skeleton 任务复用而非新建（Task 2 核心决策）**：`settle_guided_exploration`（worker.py:118-195）step 1 读答案用 `get_session_by_project` + `list_guided_answers_by_session`，free-mode 会话天然无 guided 答案 → `answers=[]` → `answeredCount=0`，陷阱⑨（worker.py:134-135「读答案空态不失败」）已兜底空态，任务仍推 progress×3 + 占位 result 跑通。V1 guided/free settle 产出都是占位 `{taskId, status:"settle_pending", answeredCount}`（无消费者、跑完即弃、零副作用，因前端全 defer + Epic 3 未实现），复用同一任务体是正确的 YAGNI；真实凝练（读 free 对话/线索 → LLM → 12 字段候选卡）是 Story 3.3 的职责（epics.md:715-717「接 Epic 2 Story 2.5/2.7 的 ARQ 任务」明写 2.5 与 2.7 共用同一整理任务交接点），届时若 guided/free 凝练逻辑分叉再由 3.3 拆分，本 story 不预判。

**门禁为何在后端做实、且为何与 2.5 不同（AC4 关键，需理解不要跳过）**：2.5 guided settle 受控决策 C 明写「不校验是否有引导答案、空答案也能跑管道」——因为引导探索的门禁语义弱（引导流程本身线性推进到收尾态，前端保证只在末题后触发，且引导答案是结构化题位、空答案也是合法状态）。**自由探索不同**：FR10 明写「自由探索的『整理为故事设定』首屏不可用，须用户补足信息并主动结束探索后才开放」——门禁「补足信息才开放」是本 story user story 的**核心 benefit**（「我不会在信息不足时得到一份空洞的设定」），不是纯 UX 修饰。加之 2.6 已确立先例「模式独立（FR5）在数据写入层真正落地，不止于前端不提供切换入口」（2.6 AC7 mode 守卫），门禁同理应在 API 层做实（前端 `disabled` + 后端 400 双防线），否则「后端门禁不存在、只靠前端按钮 disable」与 2.6 刚建立的「不止于前端」精神矛盾。此决策 2026-07-29 由 Jianghj 授权我「选最优」后定档（见 [[feedback-design-decision-delegation]]）。

**门禁近似而非精确（AC5，YAGNI）**：V1 用「≥1 条 free user 消息」近似「补足信息」，**不做**覆盖度/置信度打分（「凑齐几个线索才放行」属 EXP-P02/V2）。理由：确定性强、可测试、零 LLM 成本；真正的语义门禁需要理解对话内容质量，是 V2 的独立课题。前端 `canFinish = freeConversation.some(role==="user")`（app.js:901）与后端 `has_free_user_message` 是**同一近似的两处实现**（前后端各自判定，前端防手滑、后端防绕过），门禁文案两侧一致（都用 `formingHint` 未开放态文案）。

**mode 单一事实源（2.6 既有）**：`project.mode` 建后不可改写（2.2），`_require_project_mode` 直接查 `project.mode`（`get_owned_project` 已拿到的对象），不必额外查 `exploration_session`。

**register_task_owner / SSE 消费端点复用 2.1（陷阱⑪）**：2.1 已建 `GET /api/tasks/{taskId}/events`（含 owner 键鉴权、subscribe-first + 快照补发、owner 键 TTL=2h/snapshot TTL=1h，见 `core/sse.py`），本 story 的 free settle taskId **复用同一 SSE 消费端点**，不重建。触发端点只负责「登记属主 + 入队」，SSE 消费与任务体推事件都是既有基建。
