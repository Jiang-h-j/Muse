# Story 3.3: 探索整理为 12 字段故事设定候选卡

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 完成探索的用户，
I want 系统把我的探索内容真实整理成一份结构化的故事设定候选卡，
so that 我能看到自己模糊的念头被凝练成一份可用的设定圣经雏形。

## Acceptance Criteria

> **本 story = 把 2.5/2.7 已打通的 settle 管道 skeleton 的「占位凝练」（`worker.py:162-165` step 2）替换为真实 LLM 12 字段凝练。** 后端 only（延续 1.7→3.2 一路受控决策 A：`app.js` 零改动、前端接线 defer 到「探索前端集成切片」）。触发端点（`POST guided/settle`、`POST free/settle`）、SSE 消费端点（`GET /api/tasks/{taskId}/events`）、`story_bible` 表 + `style_profile` 列均已就绪，本 story **不新建触发/消费端点、不新建表、不加迁移**。

1. **[真实 LLM 凝练 → SSE result]** settle 任务被触发后（接 Epic 2 Story 2.5 引导收尾 / 2.7 自由「整理为故事设定」的 ARQ 任务），任务体**真实调 LLM**（经 LLMProvider 抽象，禁直调 openai）把探索材料凝练成 12 字段设定候选卡，经既有 SSE `result` 事件返回；替换 `worker.py` step 2 的占位凝练与 step 3 的占位 result（`{status:"settle_pending"}`）。[Source: epics.md#Story-3.3 AC1（715-717）；FR12（177）；worker.py:121-136,162-174（3.3 交接点 docstring）；deferred-work.md:119,159]
2. **[12 字段内容 + 消费 3.2 style_profile]** 生成的候选卡含通用主干 7 项（①genre ②core_appeal ③protagonist[姓名+核心欲望+致命缺陷] ④main_conflict[+反派镜像] ⑤world_rules ⑥overall_tone ⑦opening_hook）、题材特化 4 项（⑧power_system ⑨golden_finger ⑩romance_line ⑪faction_landscape，按 genre 激活、不匹配可空）、⑫style_profile——⑫**读取本作品 `story_bible.style_profile`（Story 3.2 已抽取值）**填充，不重抽、不覆盖。[Source: epics.md#Story-3.3 AC2（719-721）；epics.md#Epic-3（651「3.3 出卡时消费 3.2 已抽取的 style_profile」）；project_muse_setting_fields 记忆；story_bible 12 列见 3-1 story]
3. **[特化字段留空不阻塞]** V1 探索用有限问题集、不保证凑齐特化字段；某题材特化字段无对应信息时该字段留空即可、不阻塞出卡（覆盖度驱动的「凑齐才放行」属 EXP-P02/V2，本 story 不做）。主干字段无料时同样留空（对应 `story_bible` 主干列 `server_default=""`、特化列 NULL 的语义）。[Source: epics.md#Story-3.3 AC3（723-725）；3-1 story#字段表（server_default vs NULL 语义）]
4. **[genre 驱动特化激活]** genre 判别列决定特化字段是否激活：探索识别出题材（如修仙/言情）→ 对应特化字段被激活填充、不匹配的特化字段不强制填。凝练 prompt 须让 LLM 先定题材再按题材填特化项。[Source: epics.md#Story-3.3 AC5（731-733）；FR12（177）]
5. **[mode-aware 材料 + 护栏 + emit-only 边界]** 凝练任务须按会话 `mode` 取对应探索材料：guided → `list_guided_answers_by_session`；free → `list_free_messages_by_session` + `list_clues_by_session`。调 provider **之前**过 `check_quota` 护栏（托管触顶抛 429 经 SSE error 事件、BYOK 短路），Provider 层自动记账（AR14）。**本 story emit-only**：候选卡经 SSE result 返回即止，**不写 `story_bible`**——待确认卡的持久化/恢复 + revision/变化项归 Story 3.4（其 AC 明写「待确认卡真实持久化 sessionStorage→后端」）、确认写入 `story_bible` 归 Story 3.5。[Source: 受控决策 1/2（见 Dev Notes）；free_explorer_agent.extract_clues 护栏范式（:265-267,303）；3-4 story AC（epics.md:759-761）；3-5 story AC（epics.md:771-773）；deferred-work.md:119,159]

**关于「候选卡挂出为待确认设定卡」（epics.md AC 727-729：头部「Story profile / v1」、字段 `NN / 字段名` 编号呈现）**：这是**前端渲染契约**（原型 `app.js:540-559` `storyProfileDialogMarkup`），事实源是原型、前端接线 defer（受控决策 A）。本 story 后端交付**候选卡的数据契约**（SSE result payload 携带 12 字段 camelCase），前端弹卡/编号渲染在「探索前端集成切片」消费，本 story 不改 `app.js`、不回归此渲染契约。
