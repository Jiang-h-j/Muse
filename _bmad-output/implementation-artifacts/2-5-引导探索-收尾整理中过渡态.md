# Story 2.5: 引导探索——收尾「整理中」过渡态

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 答完引导全部问题的用户，
I want 看到系统正在把我的回答整理成故事设定的过渡反馈，
so that 我对「接下来会生成什么」有明确预期、且能反悔回去改。

## Acceptance Criteria

> **净新增能力只有 AC2-后端（触发整理 ARQ 任务的端点 + skeleton settle 任务）。** AC1（整理中过渡态 1.2s spinner+文案）与 AC3（回到探索复位）是**原型已实现的前端交互契约**（FR8、UX-DR4，页面即契约），
> 事实源是 `prototype/app/app.js`，本 story **不改 `app.js`、不回归这些契约**——它们由原型保持（延续 2.3/2.4 受控决策 A：后端优先、`app.js` 零改动）。本 story 只交付 AC2 缺失的后端能力：**引导收尾触发「整理为故事设定」ARQ 后台任务的端点 + 一个真实域命名的 skeleton `settle_guided_exploration` 任务**（读引导答案 → 推 progress → 推**占位 result**），复用 2.1 已建的 ARQ/SSE 底座（`POST→taskId` + `GET /api/tasks/{taskId}/events`）。**任务体的「真实调用 LLM 凝练为 12 字段设定候选卡」是 Epic 3 Story 3.3 的职责**（epics.md:715-717 明写「接 Epic 2 Story 2.5/2.7 的 ARQ 任务」→ 3.3 填真实凝练）——本 story 只把「触发 + 异步跑起来 + 经 SSE 回事件」这条管道打通、留 placeholder result 供 3.3 替换。**AC1/AC3 的浏览器端交互（过渡态渲染、回到探索复位）以及「前端发起 settle POST + 连 SSE 消费」是纯前端行为**，与 2.3 interpret 接线 + 2.4 answers 接线一并 **defer 至「引导探索前端集成切片」**（见 Dev Notes 受控决策 A）。故本 story 对 AC2 的验证边界 = **触发端点契约 + 真实入队 ARQ + skeleton 任务经 SSE 推 progress/result/error + 归属校验（IDOR）**，浏览器端过渡态→SSE 端到端由前端集成切片兑现。

1. **Given** 我作答完最后一题（FR8）
   **When** 提交末题
   **Then** 进入「整理中」过渡态（约 1.2 秒，原型 `setTimeout(..., 1200)` app.js:469-472），过渡态渲染文案「正在把你的回答整理成一份故事设定……」+ spinner（`guided-settling` 块 app.js:824-831），且过渡态**不出翻页栏**（app.js:810-812）。**本 story 后端 only，此前端交互契约由原型保持、不回归。**

2. **Given** 进入整理中过渡态（FR8，异步模型二分 epics.md:457「凝练走 ARQ 后台任务 POST→taskId→GET /events」）
   **When** 过渡态触发
   **Then** 后台以 ARQ 任务启动「整理为故事设定」（异步、不阻塞前端）。**本 story 交付此能力的后端**：① 触发端点 `POST /api/projects/{project_id}/explore/guided/settle` → 租户守卫 + 登记任务属主（陷阱②）+ 入队 ARQ `settle_guided_exploration` → 返回 `taskId`；② skeleton 任务 `settle_guided_exploration`（worker.py）：以独立 session 读本会话引导答案（复用 2.4 `list_guided_answers_by_session`）、分 step 推 `progress`、推**占位 `result`**（真实 LLM 12 字段凝练 defer 至 3.3）、异常推 `error`；③ SSE 消费**复用 2.1 已建的 `GET /api/tasks/{taskId}/events`**（不重建 tasks 路由 / sse.py）。**前端发起 settle POST + 连 SSE 消费 defer 至前端集成切片**（受控决策 A）。

3. **Given** 我在收尾态（引导完成 06/06）选择「回到探索」而非继续
   **When** 我返回
   **Then** 过渡态复位（`guidedSettling=false`，原型 `discardStoryProfileAndReturn` app.js:582-587）、回到可翻页修改的收尾态（仍可点「上一题」改答案，收尾态翻页栏 app.js:813-814）。**本 story 后端 only，此前端交互契约由原型保持、不回归**——注意：原型「回到探索」按钮在**设定卡弹窗内**（app.js:563 `data-request-profile-return` → 二次确认 → app.js:582 复位），属 Epic 3 设定卡交互域；后端不提供任何「取消整理任务」端点（ARQ 任务跑完即弃，无消费者读其 placeholder result），复位纯前端态。

4. **Given** 边界（Epic 2/3，epics.md:456）
   **When** 整理任务完成
   **Then** 本 story 职责到「触发整理任务 + 过渡态」为止；**设定候选卡的生成（真实 LLM 凝练 12 字段）、弹出、会话内恢复、确认/丢弃由 Epic 3 承接**（生成 3.3、编辑/升版 3.4、确认/丢弃 3.5）。本 story 的 skeleton 任务只推占位 result 打通管道，**不生成真实设定卡、不落库设定卡、不定义 12 字段 schema**（那是 3.1 建表 + 3.3 生成）。

### 关键实现陷阱（务必规避）

- **陷阱①：租户守卫二义合一 404（承 2.2/2.4 陷阱①）。** 触发 settle 先 `get_owned_project(session, project_id, user_id)`——None 即 404 `project_not_found`，**不写 403、不区分「不属于我」与「不存在」**（IDOR 侦察面 NFR3）。复用 `_exploration_not_found()`，勿新造 code。
- **陷阱②：`register_task_owner` 必须在 `enqueue_job` 之前（承 2.1 陷阱⑤ / tasks.py:43-47）。** 否则 worker 可能在属主键写入前就发首个 progress、SSE 端点鉴权读不到属主而对合法属主误返 404。顺序：register_owner → enqueue。
- **陷阱③：settle 是「POST→taskId」提交、非流式端点。** 触发端点返 `TaskSubmitResponse`（200 + taskId），**不返 `EventSourceResponse`**——SSE 消费是独立的 `GET /api/tasks/{taskId}/events`（2.1 已建）。别把 settle 写成 2.3 interpret 那种「端点内直接流式」（那是交互式模式；settle 是 ARQ 后台任务模式，epics.md:457 二分）。
- **陷阱④：skeleton 任务用独立 session、不复用 web 请求 session（承 2.1 陷阱⑦）。** worker 是独立进程/事件循环，从 `ctx["session_maker"]`（on_startup 备好 worker.py:113）取 session 读答案、`ctx["pub_redis"]`（:115）推事件；**绝不注入 web 请求的 `get_session`**（触发端点的 session 在 POST 返回后即 teardown，任务在别的进程跑）。
- **陷阱⑤：`WorkerSettings.functions` 必须追加 `settle_guided_exploration`（worker.py:135）。** ARQ 靠 functions 列表注册可执行任务名；漏加则 `enqueue_job("settle_guided_exploration", ...)` 入队后 worker 找不到 handler、任务静默不执行（不报错、SSE 永远收不到事件）。
- **陷阱⑥：本 story 不调 LLM、不 check_quota、不建表、不落库设定卡（受控决策 B/C）。** skeleton 任务 step 2 是占位（不 new provider、不 `provider.chat/stream`、不 check_quota）。真实凝练 + 护栏 + 设定卡持久化全归 3.3。**别在本 story 引入 `get_provider_for_user` / `check_quota` / `story_bible` 表 / 12 字段 schema**（这些是 3.1/3.3 的事）。测试不需 `@requires_deepseek`。
- **陷阱⑦：占位 result payload 必须 camelCase（承 architecture.md:336）。** 经 `sse.publish_event` 的 payload（progress 的 `{step, percent}`、result 的占位字段如 `{taskId, status, answeredCount}`）均 camelCase——`sse.format_sse_event` 只 JSON 编码不改字段名，camelCase 由构造方保证。
- **陷阱⑧：error 事件泛化对外、原始异常只落日志（承 2.1 worker.py:94-105）。** skeleton 任务 `except Exception` 推 `{"code":"settle_failed","message":"整理失败，请稍后重试。"}` + `logger.exception`（原始 exc 可能含 DB 连接串/驱动错误/内部路径，不经 SSE 外泄）+ `raise`。未来 3.3 引入 `ErrorEnvelope`（护栏 429 等）分支时透传其 `code/message`（照 worker.py:87-93 受控 envelope 分支）。
- **陷阱⑨：读答案空态不失败。** skeleton 任务 step 1 读引导答案，若会话不存在/无答案（`list_guided_answers_by_session` 返 `[]` 或 session 为 None）→ 任务仍正常推 progress + 占位 result（`answeredCount=0`），**不抛错**。前端契约保证只在收尾态（06/06 答完）触发，但任务本身不因空答案脆弱（防御性，且测试要覆盖空态跑通管道）。
- **陷阱⑩：`app.js` 一字节不改（受控决策 A）。** 引导收尾接线（settle POST + SSE 消费 + 过渡态驱动 + 回到探索复位）defer 至前端集成切片。`git status prototype/` 须为空、`fetch(` 计数保持 0。
- **陷阱⑪：不重建 tasks 路由 / sse.py（复用 2.1）。** settle 的 taskId 走 2.1 的 `GET /api/tasks/{taskId}/events` 消费（含 IDOR 归属校验、快照补发）——本 story **不在 exploration.py 里另造 SSE 消费端点**、不改 tasks.py / sse.py。触发端点只负责「入队 + 返 taskId」，消费是通用 tasks 端点的职责。
