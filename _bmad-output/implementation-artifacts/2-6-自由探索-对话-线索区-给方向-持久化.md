# Story 2.6: 自由探索——对话 + 线索区 + 给方向 + 持久化

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 选了自由探索的用户，
I want 和 Agent 自由多轮讨论、Agent 帮我自动整理线索而我仍能自己掌控，
so that 我能按自己的节奏聊出故事、且主导权始终在我手上。

## Acceptance Criteria

> **净新增能力 = AC2/AC5/AC6 的后端（自由对话真实 Agent 多轮流式 + 线索 CRUD + Agent 自动整理线索 + 真实持久化）+ mode 边界守卫补位（deferred-work.md 显式 defer 给本 story 定档）。** AC1（连续只读对话渲染、自动滚底）与 AC4（「给我一些方向」勾选+方向按钮，纯前端状态、只写输入框不代答）是**原型已实现的前端交互契约**（FR9、UX-DR5，页面即契约），事实源是 `prototype/app/app.js`，本 story **不改 `app.js`、不回归这些契约**——延续 2.3/2.4/2.5 受控决策 A（后端优先、前端接线 defer 至集成切片）。本 story 只交付后端：① 自由对话真实 SSE 流式端点 + 持久化；② 消息恢复端点；③ 故事线索 CRUD（含预设槙位播种 + 自定义增删）；④ Agent 依对话自动整理线索端点（硬 AC，用户已编辑槙位优先不被覆盖）；⑤ guided/free 两模式端点互相串门的 mode 边界守卫。

1. **Given** 我在自由探索（FR9，UX-DR5）
   **When** 对话渲染
   **Then** 连续只读呈现全部对话、不折叠不拆分（原型 `freeConversation.map` app.js:923-932），新消息自动滚到底（`conversation-scroll` app.js:947）。**本 story 后端 only，此前端交互契约由原型保持、不回归。**

2. **Given** 我发送一条消息（FR9）
   **When** Agent 回复
   **Then** 接入真实 Explorer Agent 多轮对话（流式 SSE），替代原型固定文案（原型 `freeConversation.push` 写死"这个方向值得继续展开……我不会替你直接改动设定" app.js:1084-1090）；Agent 只讨论、不替我决定或直接改设定。**本 story 交付**：`POST /{project_id}/explore/free/messages` 流式 SSE（delta→done→error，复用 2.3 interpret 的 SSE 编码范式）；用户消息与 Agent 回复均真实落库（`exploration_message` 扩展形态，AC6）。**前端发起 POST + 连流消费 defer 至前端集成切片**（受控决策 A）。

3. **Given** 右侧「故事线索」区
   **When** 我编辑线索
   **Then** 支持内联直接编辑（contenteditable，空值占位「尚未确定」，原型 `storyClue()` app.js:420-427），并可增删自定义线索（原型 `customStoryClue()` + `data-add-custom-clue`/`data-remove-custom-clue` app.js:429-437,1032-1046）。**本 story 交付后端**：`GET/POST /{project_id}/explore/free/clues`（列出/新增自定义线索）、`PATCH/DELETE /{project_id}/explore/free/clues/{clue_id}`（编辑/删除，删除仅限自定义线索）；进入自由探索时播种 4 个预设线索槙位（最初的念头/主角/核心冲突/世界与氛围）。**前端 contenteditable 交互接线 defer 至前端集成切片。**

4. **Given** 「给我一些讨论方向」复选与三个方向选项
   **When** 我勾选并点某个方向
   **Then** 只把预设句写入输入框、不代答不替我决定（原型 `data-direction` app.js:1068-1074）；勾选为会话级持续偏好、直到我主动取消（`showInspirationDirections` app.js:1030,1065）。**本 AC 完全是前端状态与静态文案，无任何后端调用（原型无 fetch）——本 story 不新增任何相关端点、不回归此契约。**

5. **Given** V1 自由模式要求 Agent 依对话自动整理线索（用户明确要求，硬 AC，非可选增强）
   **When** 对话推进
   **Then** Agent 依对话内容自动生成/更新右侧故事线索；用户已手动编辑的线索优先、不被自动整理覆盖；自动整理与手动编辑并存。**本 story 交付**：`POST /{project_id}/explore/free/clues/refresh`——同步（非 ARQ）调用真实 LLM，只读取并更新**未被用户编辑**（`user_edited=false`）的 4 个预设线索槙位，跳过已被用户编辑（`user_edited=true`）的槙位；自定义线索永不被本端点触碰（只由用户增删，非 Agent 整理对象）。「依对话推进」的触发时机（每轮对话后自动调用还是用户手动点按钮）是前端编排决定，**defer 至前端集成切片**——本 story 只交付可被随时安全调用的整理端点原语。

6. **Given** FR11 要求对话与线索真实持久化（补原型「内存态、刷新即丢」落差）
   **When** 我对话/编辑线索后刷新或断线重连
   **Then** 对话落 `exploration_message`（扩展支持自由对话形态）、线索落新建 `story_clue`（均带 `user_id`+`project_id`），可恢复。**本 story 交付**：`GET /{project_id}/explore/free/messages`（恢复对话历史，按时间升序）+ 上述 `GET /{project_id}/explore/free/clues`（恢复线索列表）。

7. **[新增] Given** 2.4 code review 显式裁定 defer 至本 story 的边界缺口（deferred-work.md「缺 guided-mode 守卫：free-mode project 可写入 guided 答案」）
   **When** 任一探索端点被调用
   **Then** 该端点校验 `project.mode` 与自身职责模式一致——guided 专属端点（interpret/answers/settle）遇 free-mode project 返回 409 `mode_mismatch`；本 story 新增的 free 专属端点（messages/clues）遇 guided-mode project 同样返回 409 `mode_mismatch`。模式独立（FR5）在数据写入层真正落地，不止于前端不提供切换入口。

    - `async def extract_clues(*, user_id, project_id) -> dict[str, str]`：Agent 整理线索（AC5）。① 重校验（同上）；② 取本会话既有 `story_clue` 中 `kind="preset"` 且 `user_edited=false` 的槙位（**只把这些槙位的 `clue_key` 提供给 LLM**——已被用户编辑的槙位连请求都不带上，从数据源头杜绝模型"顺手"改到不该碰的槙位，比事后过滤更彻底）；若无待整理槙位（全部已被用户编辑）直接返回空字典、不调用 LLM（省成本，无 AC 要求空转）；③ 取本会话全部 free 对话历史（按 `created_at` 升序）；④ system prompt 要求：读对话，为传入的槙位（按 `clue_key` 报送，如"最初的念头/主角/核心冲突/世界与氛围"其中若干个）各输出一行固定前缀格式（如 `最初的念头：<内容>`），没有新信息可提炼的槙位原样重复当前值（不杜撰未提及的内容，NFR1 红线同源约束）；`provider.chat()`（非流式，一次性小结构化输出，不需要中间态展示）；⑤ 解析响应：按固定前缀逐行匹配，只接受传入的槙位集合内的行、忽略其余（防御性——模型偏离格式也不崩溃，未成功解析的槙位保持原值不变）；⑥ 更新对应 `story_clue.value`（**不改 `user_edited`**，保持 `false`——这些行只可能是 Agent 更新过的，仍应可被后续 Agent 整理继续覆盖，直到用户真正手动编辑一次）；返回更新后的 `{clue_key: value}` 映射供响应体。

## Dev Notes

### 架构与既有模式（务必先读代码再动手，不要凭空实现）

**分层与既有约定（architecture.md）**：`routers`（仅校验+分发）→ `services`（业务）→ `repositories`（数据+租户守卫）；`orchestration/`、`services/` 调模型只能经 `providers/`（换模型后门 + 计量埋点唯一入口），**禁止业务层直接 import openai**（仅 `providers/deepseek.py` 可）。出入参 camelCase、内部 snake_case，转换点唯一在 `schemas/` 层。所有业务表必带 `user_id`+`project_id`（NFR3）。

**异步模型二分（epics.md:457，本 story 两种都用到）**：
- 交互式对话（自由聊天、引导自述理解）→ `LLMProvider.stream` 直连流式 SSE，**不走 ARQ**（自由对话、线索整理均属此类——线索整理虽非"对话"但也是一次性快速结构化提炼，非长时生成）。
- 「整理为故事设定」等凝练（2.5/2.7 已有）→ ARQ 后台任务 `POST→taskId→GET /events`。**本 story 不新增 ARQ 任务**——AC5 的线索整理与此不同类，是快档单次调用，量级/延迟都不属于 NFR2「长时生成」范畴。

**mode 单一事实源**：`project.mode` 建后不可改写（2.2 AC2/AC3），`exploration_session.mode` 只是建会话时的快照拷贝，永远与 `project.mode` 一致。故 Task 1 的 mode 守卫直接查 `project.mode`（`get_owned_project` 已拿到手的对象），**不必额外查 `exploration_session`**——省一次查询，也规避"会话尚未创建时如何判断 mode"的假问题。

**两个 Explorer Agent 模块并存、职责不重叠**：`services/explorer_agent.py`（既有，2.3）只服务引导探索"理解自述"这一件事，docstring 明写"唯一真实 LLM 职责"；本 story 新建 `services/free_explorer_agent.py` 服务自由探索的两个职责（多轮对话 + 线索整理）。**不要把新逻辑塞进 `explorer_agent.py`**，会破坏其"唯一职责"的文档承诺、也会让 guided/free 两套 mode 守卫和 system prompt 混在一个文件里增加认知负担。

**SSE 编码范式照搬 `_interpret_event_stream`**（`routers/exploration.py:56-115`）：`delta` 累积正文块、空产兜底改发 `error`（不发空 `done`）、`ErrorEnvelope` 透传 code/message、未预期异常泛化为 `generate_failed` + 日志记完整栈但不外泄。自由对话的 SSE 生成器函数结构几乎可逐行照抄，只需替换调用的编排函数（`stream_free_chat` 替代 `interpret_guided_answer`）。

**独立 session 记账安全（陷阱⑩，`services/explorer_agent.py` 模块 docstring 已详细论证）**：任何"在 web 请求上跑流式 + `MeteredProvider` 记账"的场景都必须用 `async_session_maker()` 自管 session，不依赖请求注入 session 的生命周期——早断（SSE 客户端断连）时 `MeteredProvider` 的 `finally` 记账仍需要一个存活的 session。`stream_free_chat` 与 `extract_clues` 都调用 provider，都必须遵循此范式。

**关键技术陷阱（本 story 新增，务必理解原理不要跳过）——事务内 `now()` 导致的排序坍缩**：本项目所有表的 `created_at`/`updated_at` 用 `server_default=func.now()`（`models/base.py`），PostgreSQL 的 `now()`/`CURRENT_TIMESTAMP` 在同一事务内**恒返回事务开始时刻**（不是语句执行时刻）。若把"持久化用户消息"与"持久化 Agent 回复"放在同一个 `async with session_maker() as session:` 块内只在最后 `commit()` 一次，两行会拿到**完全相同**的 `created_at`，`GET /explore/free/messages` 按 `created_at` 升序恢复时顺序不确定（同值排序无保证），破坏"连续对话记录"的可读性。**解法：用户消息写入后立即 `await session.commit()`，Agent 回复走完整个流式生成后再 `await session.commit()`**——两次 commit 天然落在两个不同事务、拿到不同的事务时刻，无需引入额外的 `sequence` 排序列（YAGNI）。

**「用户编辑优先」的实现选择（AC5 核心，[[project_muse_free_explore_clues]] 硬性要求）**：用 `story_clue.user_edited: bool` 而非更复杂的版本号/时间戳比对方案——理由：① 确定性强、可测试、易推理，不依赖"猜测哪个时间更新"这类脆弱启发式；② 更进一步的防御是**从数据源头**排除已编辑槙位——`extract_clues` 组装 LLM 请求时只把 `user_edited=false` 的 `clue_key` 报送给模型，已编辑的槙位连"存在"都不告诉模型，杜绝模型注意力被已编辑内容干扰后"顺手"在输出里带出来（即便如此，解析响应时仍只接受本次请求报送过的槙位集合内的行，双重保险，属于 NFR1 去 AI 味/克制原则的同源工程化落地）。

**为何自由对话与引导自述理解要分设两个 Agent 模块、而不是共享一个"通用聊天"函数**：引导理解（2.3 `interpret_guided_answer`）是"一题一答"单轮凝练，输出严格一句话、不维护历史；自由对话是真正的多轮上下文对话，需要组装历史消息列表喂给 `provider.stream`。二者 system prompt、消息组装逻辑、甚至护栏调用时机都不同，共享会导致条件分支缠绕，拆两个模块符合"引导 vs 自由两条链路架构上独立"的既定项目基调（epics.md:454「两链在 2.2 后并行、互不向前依赖」）。

### Review Findings

- [x] **[Review][Patch] SSE 早断/异常/空产会留下"孤儿用户消息"（Jianghj 2026-07-29 裁定采方案 b 变体）** [backend/src/muse/services/free_explorer_agent.py:stream_free_chat] — 原问题：`stream_free_chat` 在 `provider.stream` 前已单独 commit user 消息（free_explorer_agent.py:1411），此后客户端断连（`CancelledError`）、provider 抛异常、或 `answer.strip()` 为空（reasoning 吃满 max_tokens）均会导致 agent 回复不落库；`GET /free/messages` 恢复时看到仅 user 无 agent 回复的对话。前端若把"最后一条是 user"当作生成中，UI 永卡；若前端重试，产生重复 user 消息。**Blind #2 + Edge #1/#2/#3 独立三次确认。** **修法（不加列、不改迁移）**：不再在生成前 commit 用户消息；组装 LLM 历史时新用户消息只在内存里（不落库），流式生成累积完整回复、**确认 `answer.strip()` 非空后**，先 commit 用户消息（事务 A）、再 commit agent 回复（事务 B）——保留"两次独立事务 → created_at 严格递增"保序机制，无需 sequence 列。任何中断/异常/空产 → 两条均不落库，session 自动 rollback，杜绝孤儿。**同步**：`GET messages` 严格递增排序测试仍成立；新增"流中途失败/空产时用户消息也不落库"用例；`CancelledError` 因走 rollback 天然安全（对应原 defer 的 CancelledError 项一并消解）。
