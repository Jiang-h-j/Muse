# Story 3.5: 确认设定 → 只读设定圣经 + 回到探索丢弃

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 对设定满意的用户，
I want 确认后设定成为注入后续创作的只读依据、或明确丢弃重来，
so that 我的创作有稳定一致的设定地基、且反悔有明确代价提示。

## Acceptance Criteria

> **本 story = Epic 3 收官：把 3.4 落库的 pending 候选卡「收口成 confirmed 只读设定圣经」，并补「回到探索丢弃」的状态流转。** 3.4 已把 `story_bible` 的三态状态机（`draft→pending→confirmed`）+ status/revision/changed_fields 列 + pending 卡的编辑/反馈/恢复 3 端点全部建齐（done，见 3-4 story），并显式为 3.5 预留了 `confirmed` 状态位（settle 落 pending、恢复端点只返 pending，deferred-work.md:190）。**本 story 只做两件事的后端状态流转 + phase 推进**：① 确认（pending → confirmed + 作品 phase `explore→chapter`）；② 回到探索丢弃（删 pending 行或回 draft）。**后端 only**（延续 1.7→3.4 一路受控决策 A：`app.js` 零改动、前端接线 defer 到「探索前端集成切片」）——本 story 不改原型、不接前端；二次确认弹窗/取消保留是纯前端交互（见受控决策 3）。

1. **[确认设定 → 只读设定圣经 + phase 推进]** 用户在待确认设定卡点「确认故事设定 →」（原型 `data-confirm-profile`，app.js:563 / `confirmStoryProfileAndEnterChapter` app.js:590-610），后端把当前 `status='pending'` 行 `UPDATE status='confirmed'`（真实持久化到 `story_bible`，替代原型 `confirmedStoryProfile` sessionStorage app.js:593-597），并把作品 `phase` 从 `explore` 推进到 `chapter`（为 Epic 1 Story 1.6 的 phase 跳转提供真实状态——1.6 据 phase 路由「继续创作」到当前步骤）。确认后 `GET /story-profile` 恢复端点自然返 204（无 pending 卡，AC6 语义已由 3.4 建好：`get_pending_by_project` 只认 pending）。租户守卫 404、无 pending 卡 → 404 no_pending_card（复用 3.4 helper，不能确认不存在的卡）。[Source: epics.md#Story-3.5 AC1（771-773）；FR14（177）；原型 app.js:590-610；3-4 story#status 列预留（122）；deferred-work.md:190；project_service.py:20-21 `_INITIAL_PHASE="explore"` + models/project.py:35-36 phase 枚举 explore/chapter/archive]
2. **[确认后设定成只读上下文注入依据]** 确认成功后，该设定圣经作为**只读**的全文指导上下文——后续任何创作（章节生成等）读 `status='confirmed'` 行注入（FR14），不可在创作阶段被随意改写。**本 story 的落地边界**：① 确认后 `status='confirmed'`；② 编辑/反馈端点（3.4 的 PATCH/POST revise）**天然不作用于 confirmed 行**（3.4 `update_card_fields`/`revise_profile_card` 都只取 `status='pending'` 行 → confirmed 后返 None/404，只读性由此保证，本 story 无需新增拦截，但须**加测试固化**「confirmed 行不可 PATCH/revise」这一只读契约）；③ drafter 实际注入 confirmed 行是 Epic 4 的读取点（本 story 不做注入本体，只保证「确认后有一行 confirmed 可供读、且过滤得出」，deferred-work.md:190 已交接 Epic 4/5 读取须过滤 status='confirmed'）。[Source: epics.md#Story-3.5 AC2（775-777）；FR14（177）；architecture.md:212 写作注入、:227 story_bible=唯一创作依据；deferred-work.md:190（Epic 4/5 读取过滤交接）；3-4 story#受控决策 1（confirmed 读取过滤代价）]
3. **[回到探索页面 → 二次确认后丢弃当前设定与修改记录]** 用户在设定卡点「回到探索页面」（原型 `data-request-profile-return`，app.js:563），前端弹二次确认（标题「回到探索页面？」+ 正文「返回后，当前设定内容和修改记录都会丢失。」+「取消」/「确定返回」，原型 app.js:564 / `bindStoryProfileDialogInteractions` app.js:696-722）；用户点「确定返回」后调后端**丢弃当前待确认设定**（原型 `discardStoryProfileAndReturn` app.js:575-588 清 finalStoryProfile/pending/changedFields），回到可继续探索的状态。**后端语义（本 story 裁定，见受控决策 1）**：丢弃 = 删除 `status='pending'` 的 story_bible 行（回到「无待确认卡」状态，探索线索/答案仍在，可重新整理再出卡）——但**不清 style_profile 已锚定成果**（原型丢弃也不清 confirmedStoryProfile；style_profile 是 3.2 独立作品级抽取，丢弃候选卡不应丢文风锚定，故删行 vs 回退 draft 二选一见受控决策 1）。租户守卫 404、无 pending 卡 → 幂等（已无卡可丢，返成功空态或 404，见受控决策 2）。[Source: epics.md#Story-3.5 AC3（779-781）；FR15（180）；UX-DR6（157）；原型 app.js:564/575-588/696-722；3-2 story#style_profile 独立抽取]
4. **[二次确认取消 → 保留当前设定卡与修改，无变更]** 用户在二次确认弹窗点「取消」（原型 `data-cancel-profile-return`，app.js:705-710：隐藏弹窗、焦点回入口按钮），保留当前设定卡与所有修改、后端无任何变更。**这是纯前端交互**——「取消」不触任何后端请求（原型只隐藏弹窗），故**本 story 后端无对应端点/改动**，仅在 story 中显式记录此边界（前端接线切片实现弹窗与取消，本 story 不做）。[Source: epics.md#Story-3.5 AC4（783-785）；原型 app.js:705-710（取消仅隐藏弹窗、无状态变更）；受控决策 3]
5. **[确认后幕后进第一章（仅 phase 衔接，阶段规划本体归 Epic 4）]** 确认后原型幕后生成首个阶段规划、用户体感直接进第一章（原型 `confirmStoryProfileAndEnterChapter` app.js:599 `buildCurrentStagePlan` + app.js:608-609 跳 `#/projects/demo/chapters/1`）。**本 story 只做 phase 衔接**：确认时把 `phase` 推进到 `chapter`（AC1 已含），使 Story 1.6 的 phase 路由能把「继续创作」导向章节创作阶段。**阶段规划本体（幕后生成阶段目标+章节骨架，FR17）归 Epic 4 Story 4.3**，本 story 不生成任何阶段规划、不碰 drafter/编排。[Source: epics.md#Story-3.5 AC5（787-789）；FR17（Epic 4，66）；epics.md#Story-4.3（首章无缝进入-幕后阶段规划）；原型 app.js:599/608-609]

**关于前端渲染契约（原型 `storyProfileDialogMarkup` footer app.js:563-564 + `bindStoryProfileDialogInteractions` app.js:696-722）**：确认按钮 `data-confirm-profile`、回到探索 `data-request-profile-return`、二次确认弹窗 `data-profile-return-confirm`（取消 `data-cancel-profile-return` / 确定返回 `data-confirm-profile-return`）、确认后跳章节路由——这是**前端渲染/交互契约**（事实源是原型），前端接线 defer（受控决策 A）。本 story 后端交付**确认/丢弃的状态流转 API + phase 推进**；前端接线在「探索前端集成切片」消费，本 story 不改 `app.js`、不回归此交互契约。

**边界（本 story 不做）**：不做幕后阶段规划本体（Epic 4 Story 4.3 FR17）、不做 drafter 注入设定圣经（Epic 4）、不做归档页只读设定圣经展示（Epic 5 Story 5.3）、不做二次确认弹窗与取消的前端交互（前端接线切片）、不新建任何表（3.1 建表 + 3.4 加状态位已齐，本 story 零 schema 变更）、不改唯一约束（一作品一行状态流转）。

### 受控决策记录（Jianghj 2026-07-29 已授权「分歧点有先例可依时自主选最优」，[[feedback_design_decision_delegation]]）

1. **回到探索丢弃 = 删除 pending 行（非回退 draft）**。AC3「丢弃当前设定内容与修改记录」在后端裁定为 `DELETE story_bible WHERE status='pending'`。**理由**：① **原型语义对齐**——`discardStoryProfileAndReturn`（app.js:575-588）清空 finalStoryProfile/pending/changedFields 回到「无待确认卡」的探索态（可重新整理再出卡），删行精确复现「当前设定内容和修改记录都丢失」；② **一作品一行 + 三态机的自然收口**——pending 行删除后，用户重新 settle 会 get-or-create 新行（3.4 settle 落库逻辑），无残留半成品；③ **confirmed 绝对安全**——删除只 where `status='pending'`，已确认的 confirmed 圣经永不被「回到探索」误删（confirmed 不匹配）。**代价/待确认项**：删 pending 行会**连带删除该行的 style_profile**（3.2 锚定的文风，因一作品一行）——原型丢弃候选卡时确实也没保留文风到候选卡外的地方（原型 style_profile 未独立持久化）。**若产品认为「丢弃候选卡应保留文风锚定成果、免得用户回探索还得重锚文风」**，则 discard 应改为「回退 status→draft + 清 12 内容字段但留 style_profile」而非删行——**本 story 裁定删行**（简单、对齐原型、丢弃=彻底重来），此权衡登记为待确认项交创始人裁定（不阻塞开发）。**备选「回退 draft」被否**：需选择性清列（清 11 内容字段留 style_profile + 重置 revision/changed_fields），比删行复杂，且「保留文风」是产品假设未经确认——V1 从简。
2. **确认/丢弃是幂等动作、无请求体**。confirm/discard 均无入参（作用对象是「当前作品的 pending 卡」，由 path project_id + 会话 user_id 唯一确定），故端点无 request body。discard 幂等静默（无 pending 卡时丢弃不报错、返 204）——**理由**：前端「确定返回」的用户意图是「回到探索」，卡在不在都应达成该意图；重复丢弃/网络重试不应报错。confirm 则**非幂等静默**——无 pending 卡时确认返 404 no_pending_card（不能确认不存在的卡；且若已 confirmed 再 confirm，pending 查询返 None → 404，符合「已确认无待确认卡可再确认」语义）。
3. **二次确认弹窗 + 取消 = 纯前端交互，后端零参与**（AC4）。二次确认弹窗（标题/正文/取消/确定返回，原型 app.js:564/696-722）是前端 UI；「取消」只隐藏弹窗（app.js:705-710）不发任何请求；只有「确定返回」才调后端 discard。故**本 story 后端不实现弹窗/取消**，仅 discard 端点对应「确定返回」。AC4「取消保留无变更」的后端保证 = 不调 discard 就不删卡（无为而治），无需专门端点。前端弹窗接线归「探索前端集成切片」。
4. **丢弃回探索不回退 phase**。若用户已 confirmed（phase=chapter）后又想改设定，那是 Epic 4「回到设定」的场景（V1 未必支持），**不在本 story**。本 story 的 discard 只作用 pending 卡（confirmed 前的待确认态），此时 phase 仍是 explore（确认才推进 chapter），故 discard 无需动 phase。advance_phase 只在 confirm 时 explore→chapter 单向推进；V1 无 chapter→explore 回退需求（原型确认后直接进章节、无回退设定入口）。

## 待确认项（本 story 完成后交创始人/PM 裁定，不阻塞开发）

1. **【丢弃语义】删 pending 行 vs 回退 draft 保留文风**（受控决策 1）：本 story 裁定「回到探索丢弃 = 删除 pending 行」（对齐原型、简单、丢弃=彻底重来）。副作用：连带删除该行已锚定的 style_profile（一作品一行）。若产品认为「丢弃候选卡应保留文风锚定成果、免用户回探索重锚文风」，须改为「status→draft + 清 12 内容字段留 style_profile」。**建议维持删行**（原型 style_profile 未独立于候选卡持久化，丢弃即重来符合原型语义）。请确认。
