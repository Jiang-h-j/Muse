# Story 2.2: 探索会话根与模式分叉（模式独立）

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 新建作品的用户，
I want 在引导/自由二选一后进入一个独立、不会中途被切换的探索会话，
so that 我能专注在一种探索方式里、且两种方式最终产出同一套故事设定。

## Acceptance Criteria

1. **Given** 我新建作品时选了 `guided` 或 `free`（原型创建时定死 `explorationEntryMode`，写入 `sessionStorage`，app.js:1770-1774）
   **When** 我进入探索页（`#/projects/{id}/explore`，app.js:2329 `exploreMatch`）
   **Then** 系统为当前 `user_id` + `project_id` **保证存在恰好一个** `exploration_session` 记录、记下 `mode`；接口返回该会话（含 `mode`），供页面按 mode 渲染对应界面（原型 `isGuided = explorationEntryMode !== "free"` 分叉，app.js:792）。**幂等**：重复进入/刷新同一作品探索页返回同一会话、不重复建

2. **Given** 探索会话的 `mode` 是探索方式的唯一事实源
   **When** 创建 `exploration_session`
   **Then** `mode` **取自该 project 的 `mode` 列**（Story 1.4 创建作品时已落 `guided`/`free`，models/project.py:34），**不接受客户端在探索接口另传 mode**——避免前端 sessionStorage 与后端 project.mode 二源不一致；`exploration_session.mode` 与 `project.mode` 恒等

3. **Given** 我已在某一探索模式中（FR5，UX-DR5「模式独立到本次探索结束」）
   **When** 探索会话已存在且请求再次「进入探索」
   **Then** **不提供任何切换 mode 的入口/参数**——接口无 mode 入参（承 AC2）、已存在的会话 `mode` 不可被改写（幂等返回原会话，即使 project.mode 理论上不同也以已存在会话为准并保持不变）；原型无切换 UI 佐证此契约（app.js 探索页无 mode 切换控件，`explorationEntryMode` 仅新建时赋值）

4. **Given** 引导与自由两模式最终对齐同一套故事设定字段 schema（FR5，为 Epic 3 的 12 字段设定卡统一入口）
   **When** 本 story 建 `exploration_session` 表
   **Then** 表结构**与 mode 无关**（不为 guided/free 分设不同表/列）——两模式共用同一会话根，差异只在后续对话/线索的产出过程（2.3-2.7），产出终点统一（Epic 3 story_bible）。本 story **不建** `exploration_message`/`story_clue`（2.4/2.6 按需建表），**不生成任何设定**（Epic 3）

5. **Given** 探索会话数据（NFR3 行级隔离）
   **When** 任意读写 `exploration_session`
   **Then** 以 `user_id` + `project_id` 行级隔离——repository 层强制注入租户守卫，越权/不存在统一 404（延续 project_repo `get_owned_project` 范式，陷阱①「二义合一」）；他人无法读到/影响我的探索会话；`project_id` 须先校验属当前 `user_id`（防对他人 project 建会话）

### 🔑 关键设计决策：mode 单一事实源 = project.mode（AC2/AC3 的立身之本）

原型有**两个** mode 存储点：`project.mode`（作品级，1.4 已落库）与 `sessionStorage['muse-exploration-entry-mode']`（前端 UI 态）。V1 迁移后必须**定一个权威源**，否则二者漂移会导致「作品列表显示引导、探索页却渲染自由」。

**定档：`exploration_session.mode` 取自 `project.mode`（后端权威），客户端不传 mode。**
- **依据**：Story 1.4 创建作品时 `project.mode` 已按用户选择落库（`guided`/`free`，models/project.py:34、schemas/project.py:27）；architecture.md:305 定「业务数据一律走 API」——mode 是业务数据、归后端。

### 关键实现陷阱（务必规避）

- **陷阱①：租户守卫「二义合一」——越权与不存在共用同一 404，别写 403 分支。** `exploration_repo.get_session_by_project` 与 project 校验都把 `user_id` + `project_id`（或 project 的 id+user_id）**写在同一个 where**，取不到即 None→统一 404（project_repo.py:44-58 范式）。**不要**先按 project_id 查再比对 owner——那样代码里会出现「存在但不属于你」分支，易手滑返回 403 或泄露 project 存在性（IDOR 侦察面，NFR3）。
- **陷阱②：get-or-create 并发竞态——唯一约束是最终防线，别只靠「查不到就建」。** 两个请求同时进入探索、同时 miss→都走 create→双插入。**必须有 DB 唯一约束**（Task 1 的 `(user_id, project_id)` 唯一）兜底；service 层 `create+commit` 用 `try/except IntegrityError → rollback → 重查返已存在`（Task 5）。**只靠应用层「先查后建」在并发下必漏**（TOCTOU）。这与 1.5/1.7 的 check-then-act 同类，但本 story 有唯一约束可依，务必加。
- **陷阱③：mode 不可来自客户端（AC2/AC3 的技术底线）。** 接口**无 mode 入参**——mode 恒取 `project.mode`。若图省事让前端传 mode，则 sessionStorage 与 project.mode 二源漂移、且「模式不可切换」形同虚设（前端改个参数就切了）。**根除数据通道**胜过「加校验拒绝」。
- **陷阱④：命名——不叫 `session_repo`/`session_service`。** `repositories/session_repo.py` 已是 auth refresh 会话的 DAO（token_hash 直查）。探索会话用 `exploration_repo.py` / `exploration_service.py` / `schemas/exploration.py`，避免语义与文件名撞车。
- **陷阱⑤：表名单数 `exploration_session`（非复数）。** architecture.md:293 明确「表名单数 snake_case」并列出 `exploration_session`（虽 architecture.md:236/AR9 处写了复数 `exploration_sessions`，但命名规范段 L293 与 epics.md:455 均为单数——**以单数为准**，与 project/user/byok_key 现有表一致）。ORM `__tablename__` 与迁移表名都用单数。
- **陷阱⑥：本 story 不建 message/clue 表、不生成设定。** 迁移只加 `exploration_session` 一张。`exploration_message`（2.4）、`story_clue`（2.6）按需建表（epics.md:455），story_bible 设定（Epic 3）——手别痒提前建，autogenerate 只应产出一张新表（Task 8 `alembic check`）。
- **陷阱⑦：POST 幂等语义——get-or-create 返 200 而非恒 201。** projects 的 `POST` 恒新建资源→201；本接口是**幂等 get-or-create**（重复进入返同一会话）→用 200 更贴语义（Task 6）。别无脑抄 projects 的 201。
- **陷阱⑧：`app.js` 一字节不改。** 本 story 后端 only。探索页当前硬编码 `demo`、不消费路由 id（deferred-work.md:38 已授权占位）——那是 2.3/2.6 前端接线切片的事。`git status prototype/` 须为空。
