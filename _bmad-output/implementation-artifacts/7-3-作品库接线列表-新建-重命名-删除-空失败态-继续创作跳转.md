# Story 7.3: 作品库接线（列表 / 新建 / 重命名 / 删除 / 空·失败态 / 继续创作跳转）

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 已登录用户，
I want 在作品库真实管理我的多部作品，
so that 我的作品数据持久化在后端、跨设备可回到。

## Acceptance Criteria

> **本 story = 把 7.1 已建好的地基（`api.js` 的 `apiFetch`/`ApiError`）接到作品库页（`renderProjects` app.js:415-437 + `bindProjectInteractions` app.js:1807-1948），把硬编码 mock 数组 `projects`（app.js:209-240）换成后端真实作品数据。** 后端作品 CRUD（Epic 1 Story 1.4/1.5/1.6 已 done）契约稳定，前端零改动对接。**边界严守**：只接作品库页；**不接** BYOK 设置页/用量入口（7.4）、探索页（7.5/7.6）、设定卡（7.7）；不改 `api.js` 地基本身（除非发现 7.1 缺口须先在 Dev Notes 记录再动）；不改探索/章节/归档目标页函数体内部的 `demo` 硬编码返回链接（那是 7.5-7.7 的活，本 story 只保证从作品库按真实 id 跳出）；不加路由级鉴权守卫（未登录访问 `#/projects` 的全局拦截 V1 不做，业务请求 401 由 7.1 `apiFetch` 兜住跳登录）。

1. **[列表加载·多租户]** 作品库页（`#/projects`）加载时，经 7.1 `apiFetch` 调后端 `GET /api/projects` 拉取当前用户真实作品列表并渲染（FR2），替换硬编码 mock 数组 `projects`（app.js:209-240）。列表**仅呈现属于我（`user_id`）的作品**——后端从 token 拿 `current_user.id` 强制过滤、前端不传 userId（NFR3）。后端按 `updated_at DESC` 已排好序，前端直接按返回顺序渲染。[Source: epics.md#Story-7.3 AC1（1300-1302）；后端契约表 GET /api/projects → 200 `ProjectResponse[]`；project_repo.py:35-39 list_projects_by_user 按 user_id 过滤 + updated_at DESC 排序；deps.py:38 get_current_user 从 Bearer 取 user]

2. **[空态 / 失败态]** 列表为空 / 加载失败时，分别呈现原型既有 `empty` / `error` 状态位（UX-DR9），不报裸错。**关键：原型这两态当前靠 URL 预览开关 `?state=empty`/`?state=error`（app.js:432 预览面板）手动触发，非数据驱动**——本 story 须改为**真实数据态**：① `GET /api/projects` 返回空数组 `[]` → 渲染 `empty-library`「你的第一本小说，从这里开始。」（app.js:431 空分支）；② 请求抛 `ApiError`（非 401，401 由 7.1 兜住跳登录）→ 渲染 `library-error`「暂时无法读取你的作品。」+「重新加载」按钮 `[data-reload]`（app.js:431 error 分支）。「重新加载」`[data-reload]`（当前 app.js:1945-1947 仅重置 hash）须改为**重新触发列表拉取**。[Source: epics.md#Story-7.3 AC2（1304-1306）；epics.md#UX-DR9（160）；EXPERIENCE.md:106-107 empty/error 文案与行号；app.js:431 三分支渲染、:432 预览面板（接线后应弃用 `?state=` 预览改真实态）、:1945-1947 data-reload]

3. **[新建 / 重命名 / 删除真实持久化]** 对应操作调后端真实接口，成功后列表反映最新状态（FR2）：
   - **新建**：新建弹窗（`createDialog` app.js:383-413，两步 mode→naming）提交 `[data-create-submit]`（app.js:1841-1900）时，调 `POST /api/projects` 传 `{mode, title?}`（`mode` 取 `selectedMode` guided/free；`title` 取命名输入，可留空由后端回落「未命名小说」，**前端勿强制非空**）。成功返 201 `ProjectResponse`（含真实 `id`），**保留原型「新建即进探索」语义**：重置探索/章节全局态（app.js:1850-1898 既有重置逻辑）后跳 `#/projects/{realId}/explore`（把 app.js:1899 的固定 `demo` 换成真实 id）。
   - **重命名**：`•••` 菜单「重命名」内联编辑（app.js:1912-1921 触发、:1951-1955 保存），保存 `[data-save-rename]`（当前 app.js:1954 纯 DOM outerHTML）须改为调 `PATCH /api/projects/{projectId}` 传 `{title}`，成功返 200 `ProjectResponse`（含刷新后 `updatedAt`），据返回更新该行。
   - **删除**：`•••` 菜单「删除」内联二次确认（app.js:1922-1934 触发、:1959-1961 确认），确认 `[data-confirm-delete]`（当前 app.js:1961 纯 `row.remove()`）须改为调 `DELETE /api/projects/{projectId}`（成功 204 无体），成功后从列表移除该作品。**按原型交互确认后生效**（保留内联二次确认「删除后无法恢复。」，不改为 modal）。
   [Source: epics.md#Story-7.3 AC3（1308-1310）；后端契约表 POST 201 / PATCH 200 / DELETE 204；project.py schema ProjectCreateRequest（mode 必填 Literal[guided,free]、title 可空 max255）/ProjectRenameRequest（title 可空 max255）；app.js:1841-1900 新建提交、:1912-1921/:1951-1955 重命名、:1922-1934/:1959-1961 删除]

4. **[继续创作·按 phase 跳转]** 作品行主操作「继续创作」`[data-continue]`（FR3，app.js:1935-1944）点击时，读该作品后端返回的 `phase` 字段（explore/chapter/archive），经既有 `PHASE_META`（app.js:242-259，phase→路由单一数据源）跳转到当前所处创作步骤，**而非固定路由**。此逻辑 Story 1.6 已在 mock 上做实（`projects.find` + `PHASE_META[phase].route(id)`）——本 story 只须把数据源从 mock 换成真实列表，`phase` 由后端 `ProjectResponse.phase` 提供，跳转逻辑零改动。[Source: epics.md#Story-7.3 AC4（1312-1314）；后端 ProjectResponse 返回 phase（explore/chapter/archive）；app.js:242-259 PHASE_META、:1935-1944 data-continue 跳转（Story 1.6 成果）；models/project.py:36 phase 默认 explore]

5. **[未登录 / token 失效由 7.1 统一处理]** 未登录 / token 失效访问作品库、请求返 401 时，由 7.1 `apiFetch` 统一处理（自动 refresh 重放；refresh 亦失效则 `clearTokens` + 跳 `#/login?state=expired`），**不在本页重复实现**跳转逻辑。本 story 的作品列表请求经 `apiFetch`（默认 `auth:true`）发出，401 天然被兜住。[Source: epics.md#Story-7.3 AC5（1316-1318）；7.1 api.js apiFetch 401 单例刷新重放 + redirectToLogin；7.2 受控决策 3（不加路由守卫，业务请求 401 兜底）]

**边界（本 story 不做）**：不接 BYOK 设置页/用量入口（7.4）；不接引导/自由探索页（7.5/7.6）；不接设定卡/文风锚点（7.7）；不改探索/章节/归档目标页函数体内部的 `demo` 硬编码返回链接（app.js:628/1279/1425/1704/1789/2145/2323/2333/2387 等——那些是 7.5-7.7 接线时消费路由 id 的活，见 Dev Notes「已知耦合」）；不改 `api.js` 地基逻辑（新写 `projectApi` 薄封装或直接用 `apiFetch`，复用即可）；不加路由级鉴权守卫；不引入构建/打包/module（保持全局脚本）。

### error code → 前端处理映射表（AC 严格对应，不臆造）

`catch (err)`（`ApiError`，含 `code`/`detail`/`status`）后据 `err.code` 分支（`ApiError` 由 7.1 apiFetch 统一抛出）：

| 后端 code | HTTP | 触发场景 | 前端处理 |
|---|---|---|---|
| `project_not_found` | 404 | 改名/删除不存在**或不属于我**的作品（IDOR 消除，越权也返 404 不返 403，NFR3） | 提示「作品已不存在」+ 刷新列表（幂等友好） |
| `validation_error` | 422 | 请求体校验失败（mode 非法/title 超 255/projectId 非法 UUID） | 给可读提示；mode 由按钮固定传不该触发、title 超长前端可加软提示 |

| （列表加载失败·任意非 401 err） | — | 网络失败/500/502 等 | 渲染 `library-error` 态「暂时无法读取你的作品。」+ 重新加载 |

### 受控决策记录（[[feedback_design_decision_delegation]] 已授权先例可依时自主选最优）

1. **mock 副文案字段（`attention`/`detail`）后端无数据源的处置**。后端 `ProjectResponse` 只返 `{id,title,mode,phase,updatedAt}`，不返 mock 的 `attention`（「等待你」）/`detail`（「第 3 章草稿等待阅读」）。这些是原型手写的具象化文案（章节进度等），真实数据需 Epic 4/5 章节归档数据才能算出。**本 story 无这些数据源**。**建议**：projectRow 渲染时移除 `attention`/`detail` 或改为 **phase-derived 中性文案**（如 phase=explore→「设定进行中」、chapter→「创作中」、archive→「已归档」，从 PHASE_META.label 派生），不臆造后端字段、不硬编码假进度。dev 择优（移除 vs phase 派生），在 Completion Notes 说明并保持视觉不崩。**理由**：真实章节进度展示归 Epic 4/5（章节归档数据就绪后），本 story 是「作品 CRUD 接线」不含章节数据。
2. **`?state=` 预览面板（app.js:432）处置**。原型 empty/error 靠 URL 预览开关手动触发（`state-preview library-preview` 面板 3 链接）。接线后 empty/error 由真实数据驱动（空数组/请求失败）。**建议**：移除该预览面板（或保留为纯 dev 视觉工具但不再驱动真实态），确保 `?state=empty`/`?state=error` 不与真实数据态冲突（如带 `?state=empty` 访问但实际有作品应显真实列表）。dev 择优并在 Completion Notes 说明。**理由**：预览开关是 mock 期的手动态切换工具，真实数据接入后应让位给数据驱动，避免双源冲突。
3. **`GET /api/auth/me` 的封装位置 + 失败降级**。`authApi`（7.1）当前无 `me()`。**建议**：在 `authApi` 加 `me()` → `apiFetch("/api/auth/me")`（与 auth 语义内聚），或放 `projectApi`。**me 请求失败不阻断列表**：邮箱是次要信息，me 失败降级为不显示邮箱（或显占位）、列表照常渲染。**理由**：邮箱展示是 7.2 遗留的次要补全，不应因它失败而阻断作品库主功能。
4. **`renderProjects` 异步化的时序处理**。当前 `renderProjects` 同步、`render()`（app.js:2403）直接调。异步拉列表后须防「用户快速切走 hash 后回调仍写 DOM」。**建议**：渲染前记录 `location.hash`，list 回调时校验仍在 `#/projects` 才写 DOM（参照项目在途请求既有模式）；或 V1 接受简单实现（切走后写 DOM 的低概率副作用）并登记 defer。dev 择优。**理由**：与项目既有「在途 async 无取消机制」的 defer 同源（7.2 review defer 已登记同类），V1 内测期低概率，但作品库是高频入口值得轻量加固。
