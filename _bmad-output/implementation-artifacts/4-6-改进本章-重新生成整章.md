# Story 4.6: 改进本章 / 重新生成整章

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 对正文不满意的用户，
I want 用我的反馈改进本章、或干脆重写整章，
so that 我能把这一章打磨到我认可为止。

## 本 story 是「前端 mock → 真实流水线」的收口 + 后端新增修订链路

4.4 已接入首次真实生成（`POST .../generate` → 四段流水线 → SSE → 落 `chapter` 表 revision=1）。4.5 已把批注/点评/`canImprove` 开关做实（纯前端内存态），并**明确把「改进/重生真实接入」defer 到本 story**（`4-5-...md:29`，Review Defer L7/L8）。本 story 做两件事：
1. **后端新增修订链路**：`POST .../revise` 端点 + `revise_chapter` worker 任务 + service 编排 + pipeline「强制重跑 + 反馈注入」扩展 + `chapter.revision` 递增（列已存在，**无迁移**）。
2. **前端替换 mock**：把 `prototype/app/app.js:3457-3488` 的 900ms `setTimeout` mock 换成真实 `POST revise` → SSE 消费（仿 4.4 `startChapterGenFlow`/`consumeChapterGenTask`）。

## 三项受控决策（Jianghj 2026-08-05 于 create-story 阶段确认，承 [[feedback_design_decision_delegation]]）

这三项是 4.5 显式 defer 到本 story 的架构分叉，已拍板走最简路径——直接决定 AC 与数据模型：

1. **旧批注一律清空（改进 + 重生都清）**：改进本章会重写正文，旧批注的页内坐标 `{page, paragraph}` 将对不上新正文（成孤儿）。决策：**改进和重生完成后都清空 `chapterAnnotations`**（不做坐标重锚、不落库保留）。→ **直接消解 deferred-work.md:7（批注坐标错位）与 :8（locate 未钳制）两条 High/Med defer**——两条的根因都是「正文可变后旧批注坐标失真」，清空即无孤儿坐标。原型 improve mock 只清点评不清批注（app.js:3484 仅 regenerate 清），本 story **改为 improve 也清批注**（决策覆盖原型字面）。
2. **不留历史，只 `revision +1` 覆盖**：每次改进/重生 `chapter.revision += 1`、`chapter.text` 覆盖同行，**不建版本历史表、不做回看/回滚 UI**。「修订版本可追溯」（epics.md:1019）在 V1 = 版本号递增 + `chapter_generation_run` 留痕，够用。与 [[project_muse_setting_fields]] 里 story_bible revision「只计数不留史」（deferred-work.md:234）同款方法论。
3. **批注/点评不落库，随请求体一次性传**：改进时前端把内存里的 `chapterFeedback`（整体点评）+ `chapterAnnotations`（批注列表）塞进 `POST revise` 请求体传后端，用完即弃。**不新建 annotation 表、不落库**。承 4.5 决议（批注是「草稿态一次性编辑意图」，定稿即废，`4-5-...md:78`）。

## Acceptance Criteria

1. **改进本章端点 + 双侧 `canImprove` 守卫（FR20，epics.md:1005-1007，UX-DR7）**：新增 `POST /api/projects/{project_id}/chapters/{chapter_number}/revise`，body `{action: "improve", feedback?: string, annotations?: [...]}`。改进要求**具体反馈**——① 前端：无点评且无批注时「改进本章 →」按钮 disabled（`canImprove` 已在 app.js:3112）+ 点击守卫拦截（app.js:3460-3465 已在）；② 后端：`action=="improve"` 且 `feedback` 空白 **且** `annotations` 空 → 抛 400（防绕过 UI 直打，复用 `_bible_not_confirmed` 同款 ErrorEnvelope 范式，新 code `improve_feedback_required`）。改进**消费段落批注 + 整体点评作输入**，注入流水线时指令「尽量保留现有内容、只针对反馈改」。

2. **重新生成端点（epics.md:1009-1011）**：同端点 `action: "regenerate"`，**允许不填反馈**（`feedback`/`annotations` 皆可空，后端不拦）、**替换整章**、**清除旧批注**（前端 `chapterAnnotations = []`）。重生若带反馈则作「重新规划的方向参考」，不带则按设定+前文重写。

3. **强制重跑：绕过 pipeline 幂等复用（AR11，本 story 技术核心）**：改进/重生须**作废旧 `chapter_generation_run` 重跑全四段**——区别于 4.4 的幂等复用（`run_chapter_pipeline` pipeline.py:200-216：同章 run 已 succeeded 直接返旧 polisher 产物、不重跑）。触发修订前须**重置/删除该章 run 行**（清 `steps` + `status`，或删行让 pipeline 重新 `create_run`），使四段真实重跑（真计费、受 style_profile + 去AI味词表约束 NFR1）。

4. **`revision` 递增 + 覆盖（决策 2，epics.md:1015/1019）**：改进/重生成功落库时 `chapter.revision = 旧 revision + 1`、`chapter.text` 覆盖同行（`upsert_chapter` 已支持传 `revision`/`status`，chapter_repo.py:50-83）。**不留历史版本**。前端 `chapterRevision` 同步递增、**回第一页**（`chapterReaderPage = 0`，app.js:3477 语义保留）。SSE result 须带新 `revision`（前端据此更新 `chapterRevision`，不再本地 `+= 1`）。

5. **反馈注入 context-agent（AR16，扩展 4.4 写前上下文）**：`run_context_agent`（steps.py:130）扩展接收修订上下文——改进：注入「旧正文（保留基础）+ 整体点评 + 批注列表 + 保留指令」；重生：注入「可空方向反馈 + 重写整章指令」（重生不强制保留旧正文）。走 **4.2 四段流水线**（context→drafter→reviewer→polisher），style_profile + 去AI味词表约束不变（NFR1）。

6. **前端替换 900ms mock → 真实 SSE（app.js:3457-3488）**：`[data-chapter-revision]` handler 的 `setTimeout` mock 换成真实链路——`POST revise`（body 带 `action`/`feedback`/`annotations`）拿 taskId → 存 sessionStorage（刷新可接回）→ 消费 SSE progress/result/error（**仿 4.4 `startChapterGenFlow`/`consumeChapterGenTask`**，app.js:1740/1794，含 seq/projectId/chapterNumber/abort 四守卫 + 无终态兜底 + 错误退回 reading 态）。忙碌态 `chapterAgentBusy=true`、文案 improve「正在根据你的点评改进这一章……」/ regenerate「正在重新规划并生成这一章……」（app.js:3471-3473 保留）。完成后 `chapterGeneratedText` 替换为新正文、`chapterRevision` 取 SSE 的新版本号、`chapterReaderPage=0`、`chapterAnnotations=[]`（决策 1，改进也清）、`chapterFeedback=""`、`chapterAgentBusy=false`、重渲染。

7. **批注/点评随请求体传、不落库（决策 3）**：前端把 `chapterFeedback` + `chapterAnnotations` 组装进 `POST revise` body（`annotations` 建议组装为 `[{paragraph: <段落原文>, comment: <批注文本>}]`，从 `{page, paragraph}` 坐标反查 `chapterPages()` 拆段原文，给 LLM 锚点；嫌复杂可退化为纯 `comment` 文本列表）。后端 schema 收下、组装进 writing_brief、用完即弃。**不新建表、不迁移、不落库**。

8. **修订态守卫与错误处理（承 4.4 交付面）**：修订走真实异步——① 忙碌态期间按钮 disabled 防重复提交（app.js `chapterAgentBusy` 已驱动禁用，防前端双击；后端并发去重归 deferred-work.md:391 加固批次，本 story 不做）；② 生成失败（SSE error）退回 **reading 态**（保留旧正文可重看/重试，区别于 4.4 首次生成失败退 input 态）+ 可读错误提示（复用 `storyErrorText`）；③ 定稿态（`chapterFinalized`）不渲染修订按钮（app.js reading 态侧栏，4.5 已处理），无需在本 story 额外拦。
