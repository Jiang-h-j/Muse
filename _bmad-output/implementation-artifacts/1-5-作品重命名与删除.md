# Story 1.5: 作品重命名与删除

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 作品所有者，
I want 重命名或删除我的作品，
so that 我能保持作品库整洁、纠正命名。

## Acceptance Criteria

1. **Given** 我在作品库某行打开 `•••` 菜单点「重命名」（原型内联编辑，`app.js:1812-1821`）
   **When** 我输入新名（留空/纯空白则回落「未命名小说」，原型 `app.js:1849-1850`）并保存
   **Then** 系统更新该作品 `title` 并**真实持久化**（与原型仅改 DOM `title.outerHTML` 不同，`app.js:1851`），响应返回更新后的 `ProjectResponse`（含刷新后的 `updatedAt`）
   **And** 仅作品所有者可改——他人/不存在的作品返回 **404**（租户守卫 + 不泄露存在性，NFR3，见陷阱①）

2. **Given** 我点某行「删除」
   **When** 出现内联二次确认（文案「删除后无法恢复。」+「确认删除」/「取消」，原型 `app.js:1829`）且我点「确认删除」
   **Then** 系统**真实删除**该作品（与原型仅 `row.remove()` 刷新即恢复不同，`app.js:1858`），返回 **204 No Content**，列表移除该行
   **And** 仅作品所有者可删——他人/不存在的作品返回 **404**（同 AC1，NFR3）

3. **Given** 删除二次确认出现
   **When** 我点「取消」
   **Then** 确认条消失、作品保留，**不发起任何后端请求**（纯前端交互，原型 `app.js:1860-1863`），无任何变更

4. **Given** 我尝试重命名/删除某作品
   **When** 该作品不属于当前 `user_id`（或 `project_id` 根本不存在）
   **Then** 后端拒绝（租户守卫，NFR3），返回 error envelope `{code, message, detail}`（AR5），**不泄露他人作品是否存在**——「不属于我」与「不存在」返回**同一个 404**（陷阱①），不返回 403

### 🔑 本 story 唯一的关键设计判断：越权 = 不存在 = 同一个 404（陷阱①）
AC4 明确要求「**不泄露他人作品是否存在**」。这决定了错误语义：
- **不能返回 403**（Forbidden）——403 等于告诉攻击者「这个 project_id 真实存在，只是不归你」，属存在性泄露（IDOR 侦察面）。
- **必须返回 404** `project_not_found`，且「作品不属于我」与「project_id 压根不存在」返回**完全相同的响应**（同 code、同 message、同 status），攻击者无法据响应差异区分。
- **落地手法**：repo 层 `get_owned_project` 用**一条** `where(Project.id == project_id, Project.user_id == user_id)` 查询——一步过滤，取不到就是 `None`，天然二义合一。**不要**先按 id 查、再比对 `owner == current_user`（那样代码里就出现了「存在但不属于你」的分支，容易手滑返回 403，也多一次无谓查询）。
- service 把 `None` 统一 `raise _project_not_found()`（404）。改名和删除共用这一个错误工厂。

### 关键实现陷阱（务必规避）
- **陷阱①（最重要）：越权与不存在必须同码 404，见上节。** repo 一步 `where(id, user_id)` 是根治手法。测试要显式验证「越权」与「随机 UUID」返回**相同的 `code=project_not_found`**。
- **陷阱②：改名后须 `session.refresh(project)` 再返回。** `TimestampMixin.updated_at` 带 `onupdate=func.now()`，但该值在 UPDATE 语句由 DB 计算，ORM 实例内存态不会自动同步刷新的时间戳。`commit` 后调 `await session.refresh(project)` 拉回最新 `updated_at`，否则响应里的 `updatedAt` 可能仍是旧值（AC1「返回更新后的 ProjectResponse」含刷新时间）。（新建时 `create_project` 因 `flush` 后 server_default 已回填故无此问题；改名是 UPDATE，须显式 refresh。）
- **陷阱③：`ProjectRenameRequest.title` 不设 `min_length`。** 与 `ProjectCreateRequest` 同理——前端改名可留空提交，service `strip` 后回落「未命名小说」（原型 `app.js:1849-1850` `value.trim() || "未命名小说"`）。设 `min_length=1` 会 422 拒绝合法的留空提交。
- **陷阱④：改名用 `PATCH`，不用 `PUT`。** 语义上是对单一字段的部分更新（不是整资源替换），PATCH 更贴切；也为后续可能的多字段部分更新留一致风格。路径 `/api/projects/{project_id}`（RESTful 复数 + 资源 id，architecture.md:298）。
- **陷阱⑤：`DELETE` 返回 204，router 函数返回 `None` 且不设 `response_model`。** 204 No Content 不应带响应体。用 `@router.delete("/{project_id}", status_code=status.HTTP_204_NO_CONTENT)`，函数体删完直接 `return`（或无 return）。**勿返回被删对象**（那需要 200 + body，与 204 矛盾）。
- **陷阱⑥：AC3「取消删除」是纯前端、零后端请求。** 二次确认的「取消」只是移除确认条 DOM（原型 `app.js:1860-1863`），不调任何接口。**后端不需要为此写任何东西**；测试也不应臆造「取消」的后端用例。本 story 后端只交付 PATCH/DELETE 两个真正的写操作端点。
- **陷阱⑦：不碰前端。** 原型 `app.js` 的改名/删除当前是 mock（改 DOM / `row.remove()`，刷新即恢复）。V1 由本 story 提供真实端点，前端接线是**后续步骤**，本 story 一字节不改 `prototype/app/`（页面即契约、原型是唯一事实基准）。接线契约写进 Completion Notes 供后续使用。
