## 1. 靠 `sleep` 掩盖时序问题

**反模式**：用 `time.sleep()` 制造时间差，让依赖时序的断言"碰巧"通过。

**真实案例**（1-4 story，Review Patch）：`test_list_projects_ordered_by_updated_desc` 靠 `time.sleep(0.01)` 拉开 `updated_at` 时间戳来保证列表倒序——但根因是 `order_by(updated_at.desc())` 在时间戳相同时顺序不确定。修复是在 `project_repo.py:38` 补确定性次级键 `Project.id.desc()`，**而非靠 sleep**。

**为什么坏**：
- sleep 拖慢测试套件（每处累加）。
- 脆弱：`0.01s` 在 CI 高负载或低精度时钟下可能不够，偶发翻红（flaky）。
- 掩盖真实缺陷：它把"排序缺 tiebreaker"这个生产 bug 藏了起来，测试反而绿。

**正确做法**：
- 排序不确定 → 在被测代码补确定性次级键（如 `id.desc()`），测试无需 sleep。
- 需验证"时间戳确实变化" → 优先 mock 时间（`freezegun` / 注入 clock），或断言"新值 > 旧值"配合 DB server-side `now()`，而非真实 sleep。

**⚠️ 现存待清理**：`backend/tests/test_projects.py:160`（倒序测试）的 sleep 在 repo 补了次级键后**已属逻辑冗余**，应删除。`:234`（改名刷新 `updated_at`）的 sleep 也应换成 mock 时间。根因修了但测试里的 sleep 常被漏删——这正是本条要防的。

**Review 检查点**：测试里出现 `sleep` 一律要求解释——能用确定性手段（次级键 / mock 时间 / 显式设值）替代的，不放行。

## 2. 缺对称用例 / 缺守卫用例

**反模式**：只测了一半——同类操作只覆盖其一，或关键不变量无测试守卫。

**真实案例**：
- **对称缺失**（1-5 story）：PATCH 有 `test_rename_project_invalid_uuid_422`，DELETE 侧却无对应的非法 UUID 用例。同类端点覆盖不对称 → 补 `test_delete_project_invalid_uuid_422`。
- **守卫缺失**（1-8 story）：陷阱⑧"byok 行不计入托管累计"无测试守卫——**若有人误删该过滤条件，现有 12 个用例无一失败**。补 `test_sum_hosted_usage_excludes_byok_rows`，并用变异测试验证（删掉过滤条件时该用例应翻红）。

**为什么坏**：一半的覆盖给人"测过了"的错觉；关键业务不变量（谁计费、谁不计费）无守卫，回归时静默劣化。

**正确做法**：
- 写一个端点的边界用例时，问："同类的其他端点（增删改查、成功/失败）有没有对称覆盖？"
- 每条关键业务不变量至少一个"守卫用例"，并反向验证：**故意破坏被测逻辑，该用例必须翻红**（变异测试思路）。

**Review 检查点**：新增 X 的 422/404/越权用例时，检查同类 Y 是否对称覆盖；核心不变量是否有会因逻辑被删而翻红的守卫。

## 3. 断言不全（测了但没断到关键点）

**反模式**：请求发了、状态码断了，但对响应体的关键结构/字段不做完整断言。

**真实案例**（1-5 story）：4 个 404 用例仅断言 `code == "project_not_found"`，未像 401 用例那样校验错误 envelope 三要素完整 `set(body.keys()) == {"code", "message", "detail"}`。契约的一部分没被测到。

**为什么坏**：契约字段可能悄悄少给/多给/改名，测试却因只断了一个字段而全绿——契约回归漏网。

**正确做法**：断言覆盖到"契约面"——错误响应校验完整 envelope 结构，成功响应校验完整字段集（如现有 `assert set(body.keys()) == {...}` 的写法）。

**Review 检查点**：响应断言是否只测了一个字段而漏了结构？错误用例是否和成功用例用同等强度断言 envelope？

## 4. 注释误导（注释与实际测试行为不符）

**反模式**：注释声称测了 A，实际代码走的是 B；读者被注释误导，以为覆盖了某条路径。

**真实案例**（1-8 story，`test_usage.py:174`）：注释声称"用会暴露浮点漂移的成本值"，但用的是 `Decimal("0.1") + Decimal("0.2")`——Decimal 相加本就精确等于 `Decimal("0.3")`，**根本不走浮点路径**。注释让人误以为覆盖了 float 安全性，实际没有。修复：仅改注释（或改用真会漂移的 `float` 值），使注释与行为一致。

**为什么坏**：注释是给下一个人读的"覆盖承诺"。注释与行为背离，比没注释更糟——它制造虚假的安全感。

**正确做法**：注释描述的必须是代码实际执行的路径。若想测某条路径（如浮点漂移），就用真能触发它的输入。

**Review 检查点**：测试注释里的"覆盖声明"与实际输入/断言是否一致？尤其"这里测的是 X 边界"这类话，核对输入是否真触发 X。

## 5. 测试名不副实 / 测了错分支（假覆盖）

> 复盘四类之外，1-1 story 有清晰实证，补充纳入。

**反模式**：测试名声称测 A 分支，实际请求走的是 B 分支——制造虚假覆盖。与"注释误导"不同，这里是**测试意图与执行路径背离**。

**真实案例**（1-1 story）：`test_validation_error_uses_envelope` 名为测 422 校验分支，实际请求触发的是 404、走 HTTPException 分支——422 校验分支其实无覆盖。修复：拆为 `test_unknown_route_uses_http_error_envelope`（404）+ `test_validation_error_envelope_omits_input`（真正的 422）。

**为什么坏**：覆盖率报告显示"测了"，实际关键分支裸奔；改动该分支时无测试拦截。

**正确做法**：测试名承诺的分支，必须是请求实际触发的分支。构造输入时确认走的是目标代码路径（必要时打断点/看覆盖行确认）。

**Review 检查点**：测试名/意图声称的分支，与构造的输入实际触发的分支是否一致？

## 6. 脆弱测试数据致断言误报

> 复盘四类之外，1-2 story 有清晰实证，补充纳入。

**反模式**：测试用的哨兵值/夹具数据选取不当，与被测系统的输出"意外碰撞"，导致断言假失败或假通过。

**真实案例**（1-2 story）：`test_short_password_rejected_422` 初版哨兵密码用 `"short"`，恰好是 Pydantic 错误码 `string_too_short` 的子串——脱敏断言（校验响应里不含明文密码）因子串碰撞而误报。改用独特哨兵 `"a1b2c"` 后通过。

**为什么坏**：假失败浪费排查时间、动摇对测试的信任；更危险的是假通过（哨兵恰好满足断言但并非因为逻辑正确）。

**正确做法**：哨兵值/测试数据选取要与被测系统的任何输出（错误码、字段名、枚举值）**无子串/无格式重叠**，用明显人造、不可能碰撞的值（如 `"a1b2c"`、`"sentinel-xyz"`）。

**Review 检查点**：脱敏/包含类断言用的哨兵，是否可能与错误码、字段名等系统输出发生子串碰撞？

## 附：如何使用本清单

- **写测试时**：对照 6 条自查，尤其"守卫用例反向验证"（故意改坏被测逻辑，用例应翻红）。
- **Review 时**：逐条对照；发现 `sleep`、单字段断言、名不副实的测试，要求解释或修改。
- **门禁扫描**：`grep -rn "sleep" tests/` 可快速定位类别 1 的现场（当前 `test_projects.py:160,234` 待清理）。
